## 1. 到達点(結論)

**音が出ない主因は判明した。MCLK でも probe 順でもカーネルでもなく、稼働 DTB が
実機の I²C デバイス構成と一致しておらず、DTB が宣言する 0x0a に SGTL5000 が
居ないこと。** カーネル/DTB は未変更(調査は read 系のみ)。

### 決定的証拠
1. **MCLK ON でも 0x0a/0x2a は NAK**: sound ドライバを bind(戻り値
   EAGAIN=EPROBE_DEFER で probe 実行 → `mxs_saif_get_mclk` が kernel 正規シーケンスで
   MCLK 設定)した直後でも、0x0a・0x2a とも I²C 無応答。= MCLK 依存では説明不能。
2. **DTB 宣言 ⇄ 実バスが総崩れ**: 稼働 DTB(6.1.70 live device-tree)の i2c0 子ノード
   `codec@a`(sgtl5000/0x0a)/`sx8650@48`(タッチ)/`keyboard_i2c_2g@28` は
   **3 つとも NAK**。逆に **DTB 未宣言の 0x1a / 0x50 が ACK**。
   キーボードは実際 GPIO・タッチは LRADC で動作しており、DTB の I²C 版周辺は総じて
   未使用 = **EVK 由来 DTS を実機に流用しているだけ**、という像が確定。
3. dmesg `sgtl5000 0-000a: Error reading chip id -6` の真意は「MCLK 不足」でなく
   **「0x0a に誰も居ない(アドレス NAK)」**。

### 現在の問い = 「0x1a に載っているコーデックは何か」
- 0x1a は WM8960 の既定 I²C アドレスで最有力候補。
- ただし **brain-hackers の kernel(手元 5.4.149 も実機 6.1.70 も)は sgtl5000 のまま**で、
  参照できる「正しい DTS」は無い(Linux 上で PW-SH6 音声が鳴った実績も無いとみられる)。
- **回路図/teardown は入手できていない**ため、型番はソフト証拠(register dump)で
  絞るしかない。

## 2. 実機環境・確認事実

- I²C: 2 コントローラ(MXS I2C adapter)。**codec は bus0**(kernel が `0-000a` を作成)。
- bus0 の `i2cack`(アドレス ACK のみ、レジスタ read 非依存)スキャン:
  ```
  0x0a NAK   ← DTB: SGTL5000(音声)   → 実機に無し(MCLK ON でも NAK)
  0x28 NAK   ← DTB: keyboard_i2c      → 実機に無し(キーボードは GPIO)
  0x48 NAK   ← DTB: sx8650 タッチ     → 実機に無し(タッチは LRADC)
  0x1a ACK   ← DTB 未宣言             → コーデック候補
  0x50 ACK   ← DTB 未宣言             → EEPROM 候補(先頭 b0 b1 ed 68)
  0x2a NAK   ← SGTL5000 別 strap      → 無し
  ```
- 使用ツール(自作、実機 `/root`、ソース `src/`):
  - `i2cack <bus> [addr]` … アドレス ACK スキャン
  - `i2cread <bus> <addr> [n] [reg...]` … 任意アドレスのレジスタ読取り(8/16bit ポインタ)

## 3. 【本題】0x1a 全レジスタ dump(bus0、8bit ポインタ・1 バイト読み)

```
      +0 +1 +2 +3 +4 +5 +6 +7
0x00: 00 00 00 00 00 00 00 00
0x08: 00 00 00 00 05 05 06 06
0x10: 00 00 00 00 00 00 00 00
0x18: 00 00 00 00 00 00 00 00
0x20: 0a 0a 00 00 02 02 04 04
0x28: 00 00 00 00 01 01 00 00
0x30: 00 00 1c 1c 00 00 00 00
0x38: 00 00 12 12 39 39 ff ff
0x40: 00 00 00 00 00 00 00 00
0x48: 00 00 00 00 00 00 00 00
0x50: 00 00 00 00 00 00 00 00
0x58: 20 20 80 80 80 80 00 00
0x60: 80 80 80 80 00 00 00 00
0x68: 19 19 03 03 ff ff 00 00
0x70: ff ff 20 20 fb fb fb fb
0x78: de de f1 f1 f1 f1 00 00
```

### 読取りプロトコルの観察
- **隣接ペア(2k と 2k+1)が同値の箇所が多い**(0x0C/0x0D=05、0x0E/0x0F=06、
  0x20/0x21=0a…)。→ 実レジスタは **ptr>>1**(= レジスタアドレスが上位 7bit の
  WM89xx 系フォーマット)の可能性。
- 一方 0x74-0x77=fb / 0x7A-0x7D=f1 は **4 連続同値**で、単純な 16bit レジスタとも
  言い切れない。
- 2 バイト読み: ptr 0x0c→`05 06`、0x38→`00 12`、0x10→`00 00`(auto-increment は
  単バイト読みと不一致)。
- 値は 0x80/0xff/0x39/0x1c 等、**音量・制御レジスタらしい構造**でノイズではない。
  = 0x1a は実在の読取り可能なコーデック級デバイス。

### 「レジスタ = ptr>>1」で解釈した非ゼロレジスタ
```
reg 0x06=05  0x07=06  0x10=0a  0x12=02  0x13=04  0x16=01  0x19=1c
    0x1d=12  0x1e=39  0x1f=ff  0x2c=20  0x2d=80  0x2e=80  0x30=80
    0x31=80  0x34=19  0x35=03  0x36=ff  0x38=ff  0x39=20  0x3a=fb
    0x3b=fb  0x3c=de  0x3d=f1  0x3e=f1
```
→ WM8960 のレジスタ範囲(0x00-0x37)を超える 0x38-0x3e にも値があり、素の WM8960 とは
一致しない面もある。

## 3.5 追試(第3回回答「read が本物か検証せよ」への回答)

第3回回答の指摘「WM8753/8750 等は 2-wire で read 不可・Linux も cache 方式。今の
dump は幻影の可能性。register map 照合の前に read が本物か検証せよ」を受けて実施。

### (A) read は本物と確定(再現性・アドレス依存)
```
0x00 を8回:            00 00 00 00 00 00 00 00   (完全安定)
0x3e を8回:            ff ff ff ff ff ff ff ff   (完全安定)
0x32 を8回:            1c 1c 1c 1c 1c 1c 1c 1c   (完全安定)
0x00/0x3e 交互8回:     00 ff 00 ff 00 ff 00 ff   (ポインタに完全追従)
```
→ **read は完全に再現し、レジスタアドレスに正確に追従する = 本物のレジスタ読取り。**
幻影(未定義バス値)なら一様な 00/ff になるはずで、この構造化・安定・アドレス依存は
説明できない。**→ 0x1a は「読取り可能な」コーデック。**

### (B) レジスタモデル: 64 本の 8bit レジスタ(0x00-0x3f)
2 バイト読み結果:
```
ptr 0x0c → 05 06     ptr 0x0e → 06 00     ptr 0x20 → 0a 00     ptr 0x3c → 39 ff
```
- 単バイト読みはポインタ **bit0 を無視**(0x0c と 0x0d が同値)。
- 複数バイト読みは **2 バイト刻みで auto-increment**(0x0c の次が 0x0e)。
- = 実レジスタは **reg = ptr>>1** の **8bit レジスタ、0x00-0x3f の 64 本**。
  §3 の「ptr>>1 解釈」の値がそのまま 8bit レジスタ値。

### (C) 重要な帰結: 書込専用 Wolfson を除外
WM8753 / WM8750 / WM8960 / WM8731 / WM8978 は **I²C(2-wire)で register read 不可**
(Linux ドライバも regcache 方式)。**0x1a は安定して read できる**ため、これらは
**除外**される。→ 候補は「**読取り可能な 8bit・64 レジスタのコーデック**」に絞られる
(TI TLV320AIC3x 系、Everest ES83xx、Nuvoton NAU88xx、AKM AK4xxx、Cirrus 等)。

### (D) 0x50 は EEPROM ではない(読むたびに別データ)
```
seq8 1回目: 19 03 42 51 37 24 7e 90
seq8 2回目: 49 0b 34 b4 95 92 1e 92   (毎回異なる)
```
先頭も読むたび変化(b0 b1 ed 68 / d5 65 74… / 19 03…)。**安定しない = 単純 EEPROM
ではない**。乱数を返す(RNG/セキュア素子?)か、実デバイス不在で ACK のみ拾っている
可能性。基板識別情報の期待は薄い。

## 3.6 i2cread.c ソースと実トランザクション(第3回回答「i2cread を見せて」に対応)

reviewer 依頼: dump が本当に 8bit レジスタか等をトランザクション単位で解析するため
i2cread.c を提示する。**Linux 標準の regmap-I2C と同じ 2-message(write→repeated
START→read)形式**。

```c
/* i2cread <bus> <addr7> [nbytes] [reg...]
 * 例: i2cread 0 0x1a 1 0x0c  → reg ポインタ 0x0c を1バイト書いて 1バイト読む */
int nreg = (argc > 4) ? argc - 4 : 0;      /* reg バイト数(今回の dump は 1) */
unsigned char reg[8];
for (int i = 0; i < nreg && i < 8; i++)
    reg[i] = (unsigned char)strtol(argv[4 + i], 0, 0);   /* 0x0c を literal 1 バイト */

struct i2c_msg msgs[2];  int nmsgs = 0;
if (nreg > 0) {                              /* msg[0]: register ポインタ書込 */
    msgs[nmsgs].addr = addr; msgs[nmsgs].flags = 0;         /* write */
    msgs[nmsgs].len = nreg;  msgs[nmsgs].buf = reg;  nmsgs++;
}
msgs[nmsgs].addr = addr;  msgs[nmsgs].flags = I2C_M_RD;     /* msg[1]: read */
msgs[nmsgs].len = n;      msgs[nmsgs].buf = buf;  nmsgs++;
ioctl(fd, I2C_RDWR, &io);                    /* io.msgs=msgs; io.nmsgs=nmsgs */
```

### 各 dump が実際に流したトランザクション
- **§3 の全レジスタ dump** = `i2cread 0 0x1a 1 0x<reg>`(nreg=1, n=1):
  `START, 0x1a+W, <reg 1バイト>, RepSTART, 0x1a+R, <1バイト>, STOP`。
  → **register ポインタは literal 1 バイト**(0x0c は 0x0c として送出。0x18 等の
  シフトはしていない)。∴「0x0c と 0x0d が同値」等の**2バイト単位の重複は
  デバイス側の挙動**であり、ツールが ptr を細工しているわけではない。
- **2 バイト読み** = `i2cread 0 0x1a 2 0x<reg>`(nreg=1, n=2): 上と同じで read が 2 バイト。
- **ポインタ無し** = `i2cread 0 0x1a 4`(nreg=0): `START, 0x1a+R, <4バイト>, STOP`
  (register 書込なし=現在のポインタ位置から)。

> 注記(第3回回答を受けた表現修正): §3 を「register dump」と呼ぶのは早計で、
> 正しくは **「0x1a デバイスから、この 2-message read 方式で得た raw read 結果」**。
> 「reg = ptr>>1 の 8bit レジスタ」も確定ではなく解釈。ロジックアナライザで
> `1a W / <ptr> / RepSTART / 1a R / <data>` の実波形を見れば ptr 幅・data 幅が確定
> するが、測定器が無いためソフトの read-only 実験(read(0x00,2/4/8) 比較等)と
> 各 codec ドライバの regmap 形式(reg_bits/val_bits/readable_reg)照合で絞る。

### 候補の見直し(第3回回答を反映)
**WM8960 決め打ちは取り下げ**。「0x1a だから WM8960」は弱い証拠。read が本物
(§3.5)ゆえ write-only の WM8753/8750/8960/8731/8978 は本来 regmap cache のはずで
整合しにくい。**まず 0x1a の通信形式を確定 → 各 codec の I²C format(AIC23/WM8731 は
reg7/val9、WM8960 は codec 固有形式 等)と突合**して型番を絞るのが本筋。
0x50 は 8bit アドレスで 0x00-0xff を dump し基板/audio 構成のヒントを探す(read の
コスト低)。

## 3.7 追加所見: Nuvoton NAU8822 が新たな最有力候補(第3回回答の②)

0x1a の read-only 実測を Linux codec driver の register map と照合した結果、
**Nuvoton NAU8822** が新たな最有力候補として浮上(第3回セカンドオピニオン)。

- NAU8822 は **I²C アドレス 0x1a**、Linux では **7bit register / 9bit value** の
  codec(`compatible = "nuvoton,nau8822"`)。**speaker driver 内蔵**
  (0x34 LHP / 0x35 RHP / 0x36 LSPKOUT / 0x37 RSPKOUT VOLUME)で、PW-SH6 の
  音声経路(codec→speaker)として自然。§5 の PWM ブザーとの関係も再検討価値。
- register map(0x00-0x4f)の 0x2c-0x3f に INPUT/ADC/OUTPUT/MIXER/VOLUME/POWER/
  **DEVICE_REVISION(0x3e)/ DEVICE_ID(0x3f)** が連続。Linux default では
  **0x3e = 0x7f、0x3f = 0x1a**(= I²C アドレスと同じ値が DEVICE_ID に出る)。

### 決定的検証点 = reg 0x3e / 0x3f(既存 dump との照合)
`reg = ptr>>1` 仮説だと **reg 0x3e = ptr 0x7c、reg 0x3f = ptr 0x7e**。
§3 の既存 dump 末尾 `0x78: de de f1 f1 f1 f1 00 00` から:
```
reg 0x3c (ptr 0x78) = de
reg 0x3d (ptr 0x7a) = f1
reg 0x3e (ptr 0x7c) = f1   ← NAU8822 DEVICE_REVISION(default 0x7f。revision はシリコン差)
reg 0x3f (ptr 0x7e) = 00   ← NAU8822 DEVICE_ID(default 0x1a)
```
- **reg 0x3f = 00**: 単純 8bit なら NAU8822 の 0x1a と**不一致**。ただし NAU8822 は
  **9bit 値**で、1バイト読みが上位バイトなら 0x1a(=9bit `0_0001_1010`)の bit8=0 →
  上位 00 は整合。**低位バイトを取れば 0x1a のはず**。= byte order/9bit の切り分けが必要。
- ∴ **決定打は 0x7c/0x7e を 1/2/4 バイト読みして DEVICE_REVISION/ID の実値を確定**
  すること。これが NAU8822 か否かを一気に潰す。

### 次の決定実験(★実機が要る・現在デバイスはオフライン=電池切れで未実行)
```
i2cread 0 0x1a 1 0x7c   # reg 0x3e = DEVICE_REVISION?
i2cread 0 0x1a 1 0x7e   # reg 0x3f = DEVICE_ID? (NAU8822 なら 0x1a 相当)
i2cread 0 0x1a 2 0x7c   # 2バイト読みで 9bit 値の byte order を確認
i2cread 0 0x1a 2 0x7e
i2cread 0 0x1a 4 0x7c
```
+ `read(0x00, 2/4/8)` 比較で register/increment 幅を確定。NAU8822 と整合したら、
raw read を NAU8822 の 7bit/9bit regmap 形式に変換して**全レジスタを機械照合**する。

### 候補順位(第3回回答で更新)
NAU8822 ★★★★★(最優先検証) / WM8960 ★★ / WM8978 ★★ / WM8731・AIC23 ★★ /
ES83xx ★★ / WM8753 ★ / その他 Nuvoton/TI/Cirrus ★★★。
**WM8960 は取り下げ**(§3.6)。**調査は「WM8960 か?」から「NAU8822 を ID で潰す」へ切替**。

## 3.8 決定実験の結果(実機・NAU8822 の DEVICE_ID は否定的、読取りプロトコルに異常)

実機で reg 0x3e/0x3f(DEVICE_REVISION/ID)を含む拡張読取りを実施。

### (A) reg 0x3f(DEVICE_ID 位置)= 00。0x1a はどこにも出ない
連続読み(auto-increment、再現性あり)で reg 0x00-0x5f を取得:
```
reg 0x00-0x1f: 07 00 00 00 00 00 05 06 00 00 00 00 00 00 00 00 0a 00 02 04 00 00 01 00 00 1c 00 00 00 12 39 ff
reg 0x20-0x3f: 00 00 00 00 00 00 00 00 00 00 00 00 20 80 80 00 80 80 00 00 19 03 ff 00 ff 20 fb fb de f1 f1 00
reg 0x40-0x5f: 59 3e c0 81 59 3e c0 81 2b 3f d8 80 f3 24 bc a2 c3 2a 3f a0 00 00 00 00 00 02 03 00 17 00 22 00
```
- **reg 0x3e = f1、reg 0x3f = 00**。NAU8822 default(0x3e=0x7f / 0x3f=0x1a)と不一致。
- **reg 0x00-0x5f のどこにも 0x1a(=26)が現れない**。NAU8822 なら DEVICE_ID=0x1a が
  reg 0x3f に出るはずだが無い。→ **NAU8822 の決定打は否定的**。
- reg 0x40-0x4f は `59 3e c0 81` が 2 回反復するなど、有効レジスタ範囲外(ミラー/
  未初期化)の様相。

### (B) ★重要: 読取りプロトコルに異常(値が完全には信頼できない)
```
ptr 0x00 を n=1/2/4/8: 07 / 07 00 / 07 00 00 00 / 07 00 00 00 00 00 05 06
単バイト安定テスト(先に別レジスタ読取り後)の 0x00: 00 00 00 …(=07 と食い違う)
```
- **同じ reg 0x00 が、直前の読取り履歴で 07 になったり 00 になったりする**
  (連続読み=07 / 単発反復=00)。= **先頭バイトの latency か、直前アクセスに依存する
  パイプライン/ラッチ効果**がある。
- 単バイト読みは ptr bit0 無視で 2 重化するのに、連続読みは 1 レジスタ/バイトで
  increment する(ptr↔reg 対応が単発と連続で非一貫)。
- ∴ **generic な 2-message I²C read が、この 0x1a デバイスの想定 read プロトコルと
  一致していない**。raw read 値を真のレジスタ値として断定できない
  (reviewer の懸念どおり)。**確定にはロジックアナライザ、または当該コーデックの
  正式 read シーケンス適用が必要**(測定器は無い)。

### (C) 現時点の判定
- **NAU8822 は「その決定打(DEVICE_ID=0x1a)が出ない」ため、確定できないどころか
  否定寄り**。ただし read プロトコル不一致((B))のため断定はできない。
- 「0x1a は read 可能な codec」自体も、(B)を踏まえると
  「**read 要求に安定した構造的応答を返すが、それが真のレジスタ値かは未確定**」に後退。
- 次善策の候補: ①候補コーデック(NAU8822/WM8978/AIC3x 等)の**正式 read プロトコル**
  (register pointer の送り方・9bit の byte 構成・repeated-start か STOP か)を1つずつ
  試して、DEVICE_ID が既知値で読める組合せを探す。②ロジアナ/基板目視(測定器・回路図)。

> 注: 型番未確定のため DTS はまだ作らない(§5 の凍結方針維持)。
> NAU8822 確定後の DT は `codec@1a { compatible="nuvoton,nau8822"; reg=0x1a; }` +
> simple-audio-card(saif0 cpu ↔ nau8822 codec)を第一候補に検討。

## 4. 質問(セカンドオピニオンを求めたい点)

1. **§3.5 で「0x1a は読取り可能な 8bit・64 レジスタ(0x00-0x3f)コーデック」と判明した。**
   これで write-only Wolfson(WM8753/8750/8960/8731/8978)は除外されたと考えるが妥当か。
   **読取り可能で 0x1a・64 レジスタ**という条件で、TI TLV320AIC3x / Everest ES83xx /
   Nuvoton NAU88xx / AKM AK4xxx / Cirrus 等のうち**最有力**を、§3 のレジスタ値
   (device-ID/reset 値の指紋)と照合して挙げてほしい。特に **device-ID レジスタ**が
   ある型番なら、どのアドレスを読めば型番が確定できるか。
2. §3.5(B)のレジスタモデル(bit0 無視・2 バイト刻み increment)から、**8bit レジスタが
   ptr の偶数側に並ぶ**構造が読める。この癖に合致する具体的コーデックはあるか。
   低位バイト(奇数 ptr が high byte にエイリアスして取れない)を含む**完全な
   register 値の取得方法**があれば知りたい。
3. **0x50(EEPROM 候補、先頭 `b0 b1 ed 68`)** に、基板 revision / 型番 / audio 構成の
   ヒントが入っている可能性はあるか。dump する価値と読み方(アドレス幅 8/16bit)。
4. 型番が絞れた後の **i.MX28(mxs-saif)+ 当該コーデックの定石 DT**。
   SGTL5000 用 machine(`fsl,mxs-audio-sgtl5000`)は使えないので、
   **simple-audio-card で saif0(cpu)↔ codec(0x1a)** を繋ぐ形が現実的か。
   MCLK 供給方向(codec master/slave)の注意点。
5. **PWM ブザー**([20260904_タッチ音_PWM調査結論.md](20260904_タッチ音_PWM調査結論.md):
   pinmux 完全再現でも無音)との関係。アンプ enable がこの 0x1a コーデック配下だと、
   PWM は正しくてもコーデック/アンプが mute/disable で無音、という可能性はあるか。

## 5. 現状の方針(自己判断、確認求む)

- **カーネル修正は凍結**。型番未確定でドライバ/DT を作るのは早いと判断。
- 順序: **①0x1a 同定 → ②実機 HW 構成確定(0x50/電源/reset)→ ③PW-SH6 用 DTS →
  ④ALSA probe → ⑤1kHz 再生 → ⑥アンプ/スピーカ → ⑦PWM タッチ音との関係**。
- DTB 差替えは SD の p1(FAT boot)で行う(物理 SD 往復、zImage 据置)。
