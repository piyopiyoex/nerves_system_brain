# OTA 導入と USB ガジェット常時接続の停止 提案書

- 日付: 2026-09-03
- プロジェクト: hello_kiosk_brain / nerves_system_brain（PW-SH6）
- 目的: Nerves 標準の OTA（ファーム更新機構）を組み込み、それが確立した後に
  **USB ガジェット（USB-NCM）の常時接続を停止**して自立 KIOSK 化する
- 位置づけ: DevLink（自作 TCP 開発チャネル）は見送り、Nerves 正規の
  fwup ベース OTA に一本化する方針への転換

---

## 1. 背景と狙い

現状の開発・配備は手動 `populate_sd.sh` / SFTP による beam 差し替えで、
microSD 差し替えや常時 USB-NCM 接続に依存している。これを卒業し、

1. **fwup ベースの OTA** で、A/B パーティションによる安全な更新・ロールバックを得る
2. OTA が確立したら **USB ガジェットの常時接続を停止**し、KIOSK として自立動作させる
   （USB は「更新時だけ有効化」または「完全停止＋別経路更新」に）

を目指す。DevLink は crng 問題の回避には有効だが Nerves の枠外であり、
A/B・ロールバック・署名等の恩恵が無い。正規の OTA に乗るほうが最終形として堅い。

## 2. 現状（出発点）

| 項目 | 現状 |
|---|---|
| ブート | 直接 SD ブート。U-Boot(brain-hackers) が p1(FAT) の zImage + imx28-pwsh6.dtb をロード → p2(ext4) を rootfs |
| パーティション | p1: 64MB FAT（kernel/DTB/BrainLILO）/ p2: ext4 単一 rootfs |
| rootfs | **ext4**（このカーネルは squashfs 非対応） |
| 更新方式 | 手動: populate_sd.sh（SD差し替え）/ SFTP で beam 差し替え |
| fwup | **未導入**（nerves_defconfig に fwup.conf 指定なし） |
| ネットワーク | **USB-NCM のみ**。WiFi/有線なし |

## 3. 最大の技術課題（先に潰すべき不明点）

### 3.1 U-Boot が A/B ブートを扱えるか【最優先調査】

Nerves の OTA は「非稼働側パーティションに新 rootfs を書き、U-Boot 環境変数
（`nerves_fw_active` 等）で起動側を切り替える」方式。これには **U-Boot の bootcmd が
その環境変数を見て A/B を選ぶ**必要がある。

- 現状の brain-hackers U-Boot が、この A/B 切替 bootcmd を持つか不明
- p1(FAT) には `boot.scr`/`uEnv.txt` が無く、U-Boot 組込みのデフォルト bootcmd で
  起動している可能性が高い → **A/B 化には U-Boot の bootcmd 改造 or boot script 方式の導入**が要る
- U-Boot 環境変数を Linux 側から書く `fw_setenv`（uboot-env）の可否・保存先も要確認

**→ この可否が OTA 全体の成否を決める。Phase A で最初に検証する。**

### 3.2 squashfs 非対応下での atomic 更新

Nerves 標準は squashfs（read-only, 単一イメージを丸ごと書く）で atomic 性が高い。
本機は ext4 のため、rootfs パーティションを丸ごと書く（fwup の raw 書き込み）方式に
すれば ext4 でも atomic 更新は可能。ファイル単位の書き換えは避ける。

### 3.3 更新経路（USB 停止との矛盾）

WiFi/有線が無いため、OTA の転送経路は現状 USB-NCM 一択。**USB を止めると更新経路も
消える**。これは「USB 常時接続の停止」の設計そのものの論点（§5）。

## 4. OTA 方式の比較

| 案 | 方式 | 経路 | 評価 |
|---|---|---|---|
| **A** | `ssh_subsystem_fwup` + `mix upload`（またはfwupを直接 stream） | USB-NCM | Nerves 標準・追加サーバー不要。**本命**。ただし SSH は crng 課題あり → §6 |
| B | fwup ファーム(.fw)を USB メモリ / SD の FAT に置いて起動時適用 | 物理メディア | ネットワーク不要で USB 停止と両立。更新の度に物理アクセスが要る |
| C | NervesHubLink（クラウド OTA） | 要ネット | WiFi 無しのため現状不可。将来 WiFi ドングル導入時の選択肢 |

推奨: **案A を主、案B を「USB 完全停止時のフォールバック」**として併設。

## 5. USB ガジェット停止の設計（3案）

「常時接続の停止」の解釈を3通り用意し、運用に合わせて選ぶ。

| 案 | 内容 | 更新経路 | 向く用途 |
|---|---|---|---|
| **S1: オンデマンド有効化** | 通常は NCM ガジェットを構成しない。特定操作（キー長押し等）で有効化した時だけ USB-NCM が立ち上がり、案A で OTA | 更新時のみ USB | 開発継続＋自立運用の両立。**推奨** |
| S2: 完全停止 + 物理更新 | ガジェットを一切構成しない。更新は案B（USBメモリ/SD の .fw） | 物理メディア | 完全スタンドアロン |
| S3: データ用 USB のみ | NCM は止め、USB マスストレージ等に切替 | 物理 | 用途次第 |

S1 が開発の継続性と自立運用を両立でき、`enable_ethernet_gadget` を
「起動時自動」から「トリガ起動」に変えるだけで実装できる。

## 6. SSH(crng) 課題との関係

案A は SSH（`ssh_subsystem_fwup`）に乗るため、**未解決の crng ブロック問題**
（起動直後 `:crypto.strong_rand_bytes` がブロック）の影響を受ける。ただし:

- OTA は「起動直後」でなく「更新したい任意のタイミング」で行うため、crng が
  初期化済み（起動後数分〜）の状態で SSH を使えれば実用上は成立する可能性がある
- 根治はセカンドオピニオン質問書の方針（persistent seed / bootloader seed /
  jitterentropy）で別途進める
- S1（オンデマンド）なら「USB 有効化操作 → 少し待つ → OTA」の運用で crng 完了を待てる

## 7. 段階計画

| Phase | 内容 | 完了条件 |
|---|---|---|
| **A. ブート機構調査** | brain-hackers U-Boot の bootcmd / 環境変数 / fw_setenv 可否を実機調査（§3.1）。A/B 切替が可能か判定 | A/B ブートの実現可否が確定 |
| **B. fwup 導入** | nerves_system_brain に fwup.conf.eex / fwup-ops.conf を追加（rpi0 を雛形に、A/B・ext4 raw 書き込み・p1 FAT の扱いを設計）。`mix firmware` で .fw が生成できる | .fw ビルド成功、手動 fwup で A/B 書き込み確認 |
| **C. OTA 疎通** | 案A（ssh_subsystem_fwup）を組み込み、USB-NCM 経由で `mix upload` → 非稼働側更新 → 再起動で切替 → ロールバック確認 | 無線更新1往復が成功 |
| **D. USB 常時接続の停止** | S1（オンデマンド有効化）を実装。通常起動では NCM を構成せず、トリガ時のみ有効化して OTA。案B もフォールバックで用意 | 自立起動（USB 無し）で KIOSK 動作、更新時のみ USB |

Phase A で A/B が困難と判明した場合の代替: **単一 rootfs + 案B（物理メディア更新）**に
切り替える（A/B は諦め、atomic 性は fwup の raw 全書き込みで担保、ロールバックは
手動 SD 復旧）。この場合でも USB 常時停止（S2）は達成できる。

## 8. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| U-Boot が A/B 非対応 | OTA の atomic 切替不可 | §7 代替（単一rootfs + 物理更新）。または U-Boot bootcmd 改造（brain-hackers 資産の pin を崩す判断が要る） |
| crng で SSH 不安定 | 案A の OTA が起動直後不可 | 更新は crng 完了後に実施（S1 と相性良）。根治は別質問書 |
| ext4 更新中の電源断 | rootfs 破損 | fwup の raw 全書き込み（非稼働側）+ 切替は最後の1回で atomic に |
| USB 停止後に更新経路喪失 | 更新不能 | S1（オンデマンド）か案B（物理）を必ず併設 |
| p1 FAT のカーネル/DTB 更新 | カーネル更新が OTA に乗らない | 初期はカーネル固定（rootfs のみ OTA）。カーネル更新は物理更新に限定 |

## 9. まとめ / 次アクション

- **DevLink は見送り**、Nerves 正規の fwup ベース OTA に一本化
- 最初の一歩は **Phase A: U-Boot のブート機構調査**（A/B 可否の判定）。ここで
  OTA の設計（A/B か単一 rootfs か）が決まる
- USB ガジェット停止は **S1（オンデマンド有効化）を推奨**。開発継続と自立運用を両立し、
  crng 完了待ちの運用とも相性が良い
- crng 課題は OTA と切り離し、セカンドオピニオン質問書の方針で並行対応
