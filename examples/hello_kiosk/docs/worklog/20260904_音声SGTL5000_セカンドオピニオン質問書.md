## ★ 版2 追記(2026-09-04、セカンドオピニオン回答後の実機検証)

セカンドオピニオンの助言(「MCLK 論理 ON ≠ 実波形が出ている。まず I2C バス生存と
0x0a の ACK を MCLK OFF/ON で確認、電源も疑え」)を受け、**波形測定(オシロ)は
未実施**だが、ソフトで可能な範囲を検証した。

### 追加証拠1: I2C バスは生きている / 0x0a は応答しない
自作 `i2cack`(アドレス ACK のみを見る。レジスタ read 非依存)で bus0 をスキャン:
```
BUS0 scan: 0x1a  0x50        ← バスは正常動作(2 デバイスが ACK)
BUS0 0x0a: NAK (MCLK OFF時)  ← SGTL5000 想定アドレスは無応答
BUS1 scan: (none)
```
→ **I2C バス0 自体は健全**(reviewer ケース分岐の「bus 生存」は YES)。
   SGTL5000 の 0x0a は **MCLK OFF 時に ACK しない**。0x1a/0x50 の正体は未確認
   (0x50=EEPROM が定番、0x1a は別デバイス)。**MCLK ON 時の 0x0a ACK は
   次に検証予定**(reviewer ケースA/B の分岐点)。

### 追加証拠2: 稼働カーネルは 6.1.70(5.4.149 ではない)
実機 `/proc/version` = `Linux version 6.1.70-...`。§3 の 5.4.149 コード解析は
**再確認が必要**。6.1 系で該当デッドロックが既に解消されている可能性もある。

### 追加で聞きたいこと
- 6.1.70 の mxs-saif / mxs-sgtl5000 / sgtl5000 で、5.4.149 と比べ MCLK 供給
  (get_mclk / clock provider)に**既知の修正差分**はあるか。
- bus0 に 0x1a/0x50 が居る中で 0x0a だけ無応答という状況は、**SGTL5000 非実装**
  または**別アドレス実装**の可能性をどの程度示唆するか(SGTL5000 は strap で
  0x0a/0x2a)。→ **0x2a も MCLK OFF 時 NAK** 確認済み(両 strap とも無応答)。

## ★ 版3 追記(2026-09-04、第2回セカンドオピニオン回答を反映)

第2回回答で**調査の重心が変更**された。要点:

- **最優先は「PW-SH6 に SGTL5000 が本当に 0x0a に存在・給電されているか」**。
  probe 順デッドロック説は**優先度低下**(6.1 系 machine driver も get_mclk で
  11.28MHz を先に確保する設計を維持 → **カーネル改造は時期尚早**)。
- **「MCLK が無いと I2C 応答しない」を 0x0a NAK の説明にそのまま使わない**。
  bus0 で 0x50(EEPROM 定番)/0x1a が ACK = **I2C バス・controller・pull-up は
  実機で正常**。「バス故障」説はほぼ棄却。
- **0x1a が最重要**: DTS は SGTL5000=0x0a なのに ACK するのは 0x1a/0x50。
  **音声コーデックが別アドレスにいる/実機構成が EVK DTS と違う可能性**。
  0x1a を SGTL5000 と断定はできないが、正体(chip ID/register)を要確認。
- 0x0a/0x2a NAK は「非実装」だけでなく「**電源(VDDIO/VDDA)未投入**」「**RESET
  assert**」でも起きる。DTS に regulator があっても実電圧の証拠にはならない。

### 復帰後の実験計画(第2回回答の STEP、上から順に)
1. bus0 の 0x1a/0x50 正常 = 済(バス健全確定)。
2. **0x0a/0x2a を MCLK OFF/ON で ACK 比較**。MCLK ON は crude なレジスタ書きでなく
   **kernel の get_mclk が設定した実値を再現**して行う(sound ドライバ再バインドで
   get_mclk を走らせるのが確実)。
3. **MCLK 実測(オシロ): SAIF0_MCLK ≈ 11.2896MHz** ← ソフト不可・要測定器。
4. **SGTL5000 電源実測: VDDIO / VDDA / VDDD**(特に VDDIO。0V なら他が正常でも NAK)。
5. **RESET ピン状態**。
6. **0x1a の正体調査**(chip ID/register read。音声コーデックらしい応答が出れば
   「DTS の audio codec が実機と違う」方向へ一気に展開)← `i2cread` ツール用意済み。
7. **PW-SH6 回路図 / PCB で SGTL5000 実装確認**。
8. linux-brain 6.1.70 の mxs-saif/mxs-sgtl5000 を mainline と diff(device-free)。
9. 以上で必要と判明して初めてカーネル修正。

### 次の一手(たった2つ、実機復帰後すぐ)
- **① MCLK ON 時の 0x0a ACK**(OFF=NAK は確認済み。ON で ACK すれば MCLK 依存確定)。
- **② 0x1a の正体**(`i2cread 0 0x1a ...` で先頭レジスタ読取り)。
  → 0x1a が音声コーデックらしければ、本件は MCLK でも probe 順でもなく
  「PW-SH6 の audio codec が DTS と違う」方向へ展開。

> ツール: `src/i2cack.c`(ACK 確認)/ `src/i2cread.c`(任意アドレスのレジスタ読取り、
> 8/16bit ポインタ対応)を用意済み。実機復帰後に `/root` へ配備して STEP2/6 を実行。

## ★★ 版4 追記(2026-09-04、決着 — 第2回回答の「次の一手2つ」を実機実行)

第2回回答の推奨(①MCLK ON での 0x0a ACK、②0x1a の正体)を実機で実行し、**主因が
確定**した。**音が出ないのは MCLK でも probe 順でもカーネルでもなく、稼働 DTB が
実機の I2C 構成と一致しておらず、0x0a に SGTL5000 が居ないこと**。詳細:
[20260904_音声調査結論_DTBと実機I2C不一致.md](../adr/0004-音声_DTBと実機I2C不一致.md)。

### 決定実験の結果
- **実験①**: sound ドライバを bind(戻り値 EAGAIN=EPROBE_DEFER で probe 実行 →
  `mxs_saif_get_mclk` が kernel 正規シーケンスで MCLK 設定)した**直後**でも
  **0x0a / 0x2a とも NAK** = reviewer ケースB(MCLK 依存でない)。
- **実験② + DTB 突合**: 稼働 DTB(6.1.70 live device-tree)が i2c0 に宣言する
  `codec@a`(sgtl5000/0x0a)/`sx8650@48`(タッチ)/`keyboard_i2c_2g@28` は
  **3 つとも NAK**。逆に **未宣言の 0x1a / 0x50 が ACK**。キーボードは実際 GPIO・
  タッチは LRADC で動作 → DTB は EVK ボイラープレートで実機と不一致。

### 現在の理解
- dmesg `sgtl5000 0-000a: Error reading chip id -6` の真意は「MCLK 不足」でなく
  **「0x0a に誰も居ない(アドレス NAK)」**。カーネル改造(mxs-saif MCLK 等)は不要。
- **実コーデックは 0x1a**。WM8960 の既定 I²C アドレスが 0x1a で最有力。ただし
  **brain-hackers の kernel(5.4/6.1 とも)は sgtl5000 のまま = 正しい DTS 参照先なし**。
  実機 0x1a は 8bit レジスタで概ね一貫した読値(0x0C-0x0F=05/05/06/06、他 0)を返すが、
  WM8960 は本来 write-only のため断定不可。**回路図/teardown は入手できていない**。

### 版4 で聞きたいこと
1. bus0 で **0x1a が ACK・8bit レジスタで一貫読値**、かつ 0x0a(SGTL5000)不在という
   状況から、**0x1a のコーデックを WM8960 と見てよいか**、他候補(TLV320AIC23/AIC3x、
   WM8731/8978、ES8388 等)をどう絞るか。**read 可否や register map の指紋**で
   ソフトのみで part を絞る現実的手法は?(0x1a の全レジスタ dump は提供可能)
2. **回路図なしで WM8960 を仮定して進める**リスクと妥当性。DT を
   `wm8960@1a`(`wlf,wm8960`)+ 対応 machine(simple-audio-card か fsl,imx-audio-wm8960)
   にし、`CONFIG_SND_SOC_WM8960` を有効化して**試行錯誤で当てにいく**のは妥当か。
   WM8960 と実機で MCLK 供給方向(codec master/slave)・SAIF 設定の注意点。
3. i.MX28(mxs-saif)+ WM8960 の**動作実績・定石 DT**はあるか。SGTL5000 用の
   `fsl,mxs-audio-sgtl5000` machine は使えないので、**simple-audio-card** で
   saif0(cpu)↔ wm8960(codec)を繋ぐ形が現実的か。
4. 0x50(EEPROM らしい、読値 `b0 b1 ed 68`)に**コーデック種別や音声構成のヒント**が
   入っている可能性はあるか。読む価値はあるか。

## 0. 要約(結論を先に)

SGTL5000 コーデックが `Error reading chip id -6`(ENXIO)で probe 失敗し、
ALSA サウンドカードが出ない。原因は既知の「**SGTL5000 は MCLK が無いと I2C にすら
応答しない**」問題と、**probe 順デッドロック**の複合と考えていた。しかし実機で
**SAIF0 の MCLK 出力を有効化(RUN=1 / CLKGATE クリア / ソースクロック ungate /
MCLK パッド pinmux 正常)した状態でコーデックを再バインドしても、依然 ENXIO** で
応答しない。ソフト(レジスタ + sysfs rebind)では復活できなかった。この
「MCLK を出したはずなのに I2C 応答しない」原因の切り分けについて意見を求めたい。

## 3. コード読解で特定した「probe 順デッドロック」

1. `sgtl5000_i2c_probe()`(codecs/sgtl5000.c:1599-1626):
   `devm_clk_get()`→`clk_prepare_enable(mclk)`→`udelay(1)`→
   **`regmap_read(SGTL5000_CHIP_ID)` で ENXIO**。これは**ハード失敗**で
   `-EPROBE_DEFER` ではないため、**I2C デバイスは再 probe されない**。
2. `mxs_saif_mclk_init()`(mxs/mxs-saif.c:705-730):
   `<&saif0>` の実体は `clk_register_divider("mxs_saif_mclk", parent=saif->clk,
   reg=SAIF_CTRL, field=BITCLK_MULT_RATE)`。**単純な divider で gate を持たない**。
   → コーデックが `clk_prepare_enable` してもこの divider(親 SAIF clk)を回すだけで、
   **MCLK ピン出力に必要な `SAIF_CTRL` の CLKGATE クリア + RUN セットはしない**。
   RUN を立てるのは `mxs_saif_get_mclk()`(同 238-284)のみ。
3. `mxs_sgtl5000_probe()`(machine)は probe 内で `mxs_saif_get_mclk(0, 44100*256,
   44100)` を呼ぶ(RUN を立てる)が、その後 `snd_soc_register_card()` が
   **コーデック未登録で -EPROBE_DEFER** → machine driver は「deferred pending」で停止。
   → コーデックは MCLK 待ちで死に、MCLK を立てる machine は コーデック待ちで停止、の**相互待ち**。

## 4. 実機検証(devmem + sysfs、すべて実測)

「MCLK を出せばコーデックが応答するはず」を検証した。SAIF0 base=0x80042000。

| 項目 | レジスタ | 実測 | 判定 |
|---|---|---|---|
| SAIF_CTRL RUN(bit0) | 0x80042000 | **1** | MCLK 出力 ON |
| SAIF_CTRL CLKGATE(bit30) | 0x80042000 | **0** | ungated |
| SAIF_CTRL SFTRST(bit31) | 0x80042000 | 0 | not reset |
| MCLK パッド pinmux | MUXSEL7 bits8-9(bank3 pin20) | **0=SAIF0_MCLK** | 正常 |
| CLKCTRL_SAIF0 CLKGATE(bit31) | 0x800400c0 | 1(idle時) → **手動で0にも** | ソースclk |
| CLKSEQ | 0x800401d0 | 0x00000104 | — |
| FRAC0 | 0x800401b0 | 0x5e5e1652 | — |

- machine driver の deferred probe が実際に `get_mclk` を実行しており、
  **SAIF_CTRL は RUN=1 / CLKGATE=0** の状態だった(＝MCLK 出力は有効化済み)。
- それでも **`/sys/bus/i2c/drivers/sgtl5000/bind` に `0-000a` を書いて再 probe
  させると、依然 `chip id -6`**。
- さらに **CLKCTRL_SAIF0 のソースクロックゲートを手動で開けて(bit31=0)**から
  rebind しても、同じく `chip id -6`。
- 検証後はレジスタを元に戻した(SAIF0 再ゲート)。LCD/バックライトには触れていない。

## 5. こちらの仮説(要検証)

1. **MCLK 周波数が正しく生成されていない**: 手動 ungate では ref_pll 分数分周
   (SAIF fractional / CLKSEQ / FRAC)を `clk_set_rate` 相当で設定していないため、
   MCLK が 0Hz か想定外周波数で、コーデックが 8 クロックを得られず ACK しない可能性。
   カーネルの `mxs_saif_set_clk`(clk_set_rate 512×fs)を通さないと正しい MCLK に
   ならないのでは。
2. **コーデック電源(VDDA/VDDIO=reg_3p3v)未投入**の可能性。
3. **I2C バス自体 or コーデック実装の問題**(バス0の他デバイス応答は未確認、
   コーデック非実装/別品番の可能性も排除しきれていない)。
4. **probe 順デッドロックの解消が本丸**: たとえ MCLK が出ても、コーデックが
   一度ハード失敗すると再試行されないため、`-EPROBE_DEFER` 化 or ドライバ順序
   制御が必要。

## 6. 質問(セカンドオピニオンを求めたい点)

1. **MCLK を出力しているはずなのに SGTL5000 が I2C 応答しない**主因として、
   上記のうちどれが最も疑わしいか。特に「RUN=1 + CLKGATE=0 + pinmux 正常」でも
   **ソースクロックの分数分周(clk_set_rate)を通さないと MCLK は実質出ない**、
   という理解は正しいか。
2. i.MX28 + SGTL5000 のこの**probe 順デッドロック**に対する**定石の修正**は何か。
   候補: (a) `mxs-saif` の `mxs_saif_mclk` を **gate 付きクロック**にして
   `.enable` で CLKGATE クリア + RUN セット(＝コーデックの `clk_prepare_enable`
   で MCLK が実際に出る)、(b) `mxs_saif_probe` で master SAIF の MCLK を
   **ブート時に常時 ON**(デフォルト rate で `set_clk`+RUN)、(c) コーデック側で
   chip id 読取り失敗を `-EPROBE_DEFER` にして MCLK 確立後に再試行、
   (d) mainline に既存の該当コミットがあるか。**推奨と副作用**を知りたい。
3. **カーネル再ビルドを避けた回避策**は現実的か。例えば起動時に userspace から
   ①正しい MCLK を出す(必要な CLKCTRL/FRAC/SAIF_CTRL シーケンス)→
   ②`sysfs` でコーデックを bind、という手順で音声パスを確立できるか。
   できる場合、**MCLK を正しく出すための最小レジスタ操作列**を知りたい
   (ref_pll→SAIF の分数分周設定を含む)。
4. そもそも **PW-SH6 実機に SGTL5000 が載っているか / この I2C 経路が正しいか**を
   ソフトから確定する方法(MCLK 非依存で I2C バスの生存やコーデック実在を確認する手)。
5. 本件は **PWM ブザー**の件とも関連する
   ([20260904_タッチ音_PWM調査結論.md](../adr/0002-タッチ音_PWM調査結論.md): PWM 経路は
   pinmux 完全再現でも無音)。ブザーの発音も実は **SGTL5000 音声経路**に依存する
   可能性はあるか(アンプが同一コーデック配下か)。
