# 音声調査 結論: 稼働 DTB が実機 I2C 構成と不一致(SGTL5000 は実機に居ない)

> **位置づけ**: この文書は調査・検証の詳細記録です。現在の判断は [`../adr/0004-音声_DTBと実機I2C不一致.md`](../adr/0004-音声_DTBと実機I2C不一致.md) を参照してください。

> **【方針転換 2026-09-05】オンボード音声は回路情報の壁で凍結。音声の本命は USB オーディオ。**
> 実機カーネルに `CONFIG_SND_USB_AUDIO=y` / `CONFIG_USB_CHIPIDEA_HOST=y` が既に組込済みで、
> コーデック同定(0x1a)の壁を丸ごと迂回できる。USB ホスト有線 LAN の Phase 0 と一体で進める。
> 詳細: [20260905_音声方針転換_USBオーディオ.md](../adr/0006-USBオーディオを採用する.md)

- 日付: 2026-09-04
- プロジェクト: hello_kiosk_brain(SHARP Brain PW-SH6)
- 前提: [20260904_音声SGTL5000_セカンドオピニオン質問書.md](20260904_音声SGTL5000_セカンドオピニオン質問書.md)(版3)
- 結論: **音声が出ない主因は MCLK でも probe 順でもカーネルでもない。稼働 DTB
  (EVK 由来)が実機の I2C デバイス構成と一致しておらず、SGTL5000 driver が
  「何も居ない 0x0a」を叩いていた。実機の音声コーデックは 0x1a にいる公算大。**

---

## 1. 決定実験と結果(第2回セカンドオピニオンの「次の一手2つ」)

### 実験①: MCLK ON での 0x0a ACK → NAK(ケースB 確定)
sound プラットフォームドライバを bind(`echo sound > .../mxs-sgtl5000/bind` = 戻り値
EAGAIN=EPROBE_DEFER で probe 実行 → `mxs_saif_get_mclk` が **kernel の正規シーケンス
(clk_set_rate 512×fs + RUN)** で MCLK 設定)した**直後に** `i2cack`:
```
0x0a: NAK   0x2a: NAK   ← MCLK ON でも SGTL5000 想定アドレスは無応答
```
→ reviewer ケース分岐の **ケースB(MCLK OFF=NAK / ON=NAK)**。
   = **MCLK 依存では説明できない。probe 順/カーネル修正は追わない。**

### 実験②: 0x1a の正体 → 未宣言の live デバイス(書込専用コーデック的)
`i2cread` で 0x1a を読むと **8bit レジスタ方式で応答するが読値が不安定**
(reg 0x00 が 07 だったり 00 だったり)。これは **書き込み専用の制御 I/F を持つ
コーデック(Wolfson WM8960 系。既定 I2C アドレスが 0x1a)** の典型挙動。
SGTL5000(16bit レジスタ・0x0a・要 MCLK)とは別物。

## 2. 決定的証拠: DTB 宣言と実バスが総崩れで不一致

稼働カーネル(**Linux 6.1.70**)の device-tree(`/proc/device-tree`)i2c@80058000
= `/dev/i2c-0`(= kernel が `0-000a` を作成した実バス)の子:
- `codec@a`(fsl,sgtl5000, 0x0a)/ `sx8650@48`(semtech タッチ)/ `keyboard_i2c_2g@28`

これに対し実バス0を `i2cack` でスキャン:
```
0x0a NAK   ← DTB: SGTL5000(音声)      → 実機に無し
0x28 NAK   ← DTB: keyboard_i2c         → 実機に無し(キーボードは実際 GPIO)
0x48 NAK   ← DTB: sx8650 タッチ        → 実機に無し(タッチは実際 LRADC)
0x1a ACK   ← DTB 未宣言                → 実機に居る(音声コーデック?)
0x50 ACK   ← DTB 未宣言                → 実機に居る(EEPROM。読値 b0 b1 ed 68)
```
**DTB が宣言する i2c0 デバイスは 3 つとも無応答、逆に未宣言の 2 つが応答。**
= 稼働 DTB は EVK ボイラープレートで、実機 PW-SH6 の周辺構成と合っていない。
キーボードが GPIO・タッチが LRADC で動いている事実とも整合(DTB の I2C 版は未使用)。

## 3. これまでの調査の位置づけ(何が誤解だったか)

- 「SGTL5000 が MCLK 待ちで I2C 応答しない/probe 順デッドロック」という筋は、
  **そもそも 0x0a に SGTL5000 が居ない**ため的外れだった。dmesg の
  `sgtl5000 0-000a: Error reading chip id -6` は「MCLK 不足」ではなく
  **「0x0a に誰も居ない(NAK)」**が真の意味。
- SAIF/MCLK レジスタ(RUN/CLKGATE/pinmux)を完全再現しても無音だったのも当然。
  叩く先のコーデックが居ないのだから。
- 第2回セカンドオピニオンの読み(「0x1a が音声コーデック/実機が DTS と違う」)が
  当たった。

## 4. 修正方針(音声パス確立の本筋)

1. **0x1a のコーデックを特定**する。WM8960 と仮定し、
   - 回路図 / brain-hackers の PW-SH6 情報で実チップを確定(最確実)。
   - あるいは書込専用前提で WM8960 として DT を試す(compatible=`wlf,wm8960`,
     reg=0x1a、machine=`fsl,imx-audio-wm8960` or simple-audio-card + SAIF)。
2. **DTB を実機に合わせて修正**: codec@a(sgtl5000)を実チップ(例 wm8960@1a)へ差替え、
   sound machine を対応ドライバへ。SAIF 配線(MCLK/LRCLK/BITCLK/SDATA)は流用可。
3. カーネルに対象コーデックドライバ(例 `snd-soc-wm8960`)が有効か確認
   (6.1.70 の config)。無ければ有効化。
4. **DTB 差替えは SD の p1(FAT boot)** で行う(物理 SD 往復)。zImage は据置、DTB のみ。

## 4.5 コーデック特定の状況(回路図なし・Web 調査)

- **WM8960 の既定 I²C アドレスは 0x1a**(NXP/各社資料で確認)。実機スキャン結果と一致。
  → 0x1a のコーデックは **WM8960 が最有力候補**。
- ただし **brain-hackers の kernel は 5.4.149(手元)も実機 6.1.70(live DTB)も
  両方 sgtl5000@0x0a のまま**。= コミュニティ側も未修正で、参照できる「正しい DTS」は
  存在しない。Linux 上で PW-SH6 の音声が鳴った実績は無いとみられる。
- 実機 0x1a のレジスタ読取りは概ね一貫(0x0C-0x0F=05/05/06/06、他 0)だが、
  WM8960 は本来**書込専用**(read 不可)なので、この読値は WM8960 なら副作用の可能性。
  **0x1a=WM8960 と断定はできない**(別の 0x1a コーデック — TLV320AIC23/AIC3x 等 —
  の可能性も残る)。
- **確定には基板の目視(音声チップのマーキング)/ teardown 写真 / 回路図が必要。**
  回路図が手元に無いため、ここで部品確定は保留。

## 4.6 0x1a 全レジスタ dump(Phase 1: コーデック同定、オフライン照合用)

第3回セカンドオピニオンの指示「カーネルも DTB も触らず、まず 0x1a の全レジスタ
dump を取る」に従い取得(bus0=/dev/i2c-0、`i2cread` で 8bit ポインタ・1バイト読み)。

```
      +0 +1 +2 +3 +4 +5 +6 +7
0x00: 00 00 00 00 00 00 00 00
0x08: 00 00 00 00 05 05 06 06
0x10: 00 00 00 00 00 00 00 00
0x18: 00 00 00 00 00 00 00 00
0x20: 0a 0a 00 00 02 02 04 04
0x28: 00 00 00 00 01 01 00 00
0x30: 00 00 1c 1c 00 00 00 00
0x38: 00 00 12 12 39 39 ff ff
0x40: 00 00 00 00 00 00 00 00
0x48: 00 00 00 00 00 00 00 00
0x50: 00 00 00 00 00 00 00 00
0x58: 20 20 80 80 80 80 00 00
0x60: 80 80 80 80 00 00 00 00
0x68: 19 19 03 03 ff ff 00 00
0x70: ff ff 20 20 fb fb fb fb
0x78: de de f1 f1 f1 f1 00 00
```

### 読取りプロトコルの観察(重要)
- **隣接ペア(2k と 2k+1)が同値になる箇所が多い**(0x0C/0x0D=05、0x0E/0x0F=06、
  0x20/0x21=0a…)。= **実レジスタは 8bit ポインタ>>1**(WM8960 系の「レジスタ
  アドレスは上位7bit + 9bit データ」フォーマットと整合)の可能性。
- ただし 0x74-0x77=fb(4連続)・0x7A-0x7D=f1(4連続)のように**2 の倍数で割り切れない
  繰返し**もあり、単純な 16bit レジスタとも言い切れない。
- 2バイト読み: ptr 0x0c→`05 06`、0x38→`00 12`、0x10→`00 00`。auto-increment 挙動は
  単バイト読みと一致せず(0x0c の次バイトが 0x0d でなく 0x0e の値)。
- 値は 0x80/0xff/0x39/0x1c/0x12 等、**音量・制御レジスタらしい構造**を持ち、
  ノイズ/フロートではない。= 0x1a は実在する読取り可能なコーデック級デバイス。

### 「レジスタ = ptr>>1」で解釈した場合(WM8960 候補として)
reg 0x06=05, 0x07=06, 0x10=0a, 0x12=02, 0x13=04, 0x16=01, 0x19=1c, 0x1d=12,
0x1e=39, 0x1f=ff, 0x2c=20, 0x2d=80, 0x2e=80, 0x30=80, 0x31=80, 0x34=19, 0x35=03,
0x36=ff, 0x38=ff, 0x39=20, 0x3a=fb, 0x3b=fb, 0x3c=de, 0x3d=f1, 0x3e=f1。
→ **WM8960 のレジスタ数(0x00-0x37)を超える 0x38-0x3e にも値**があり、単純な
WM8960 とは一致しない面もある。**型番はこの dump を各コーデックの register map と
照合して確定する(オフライン作業)。**

## 5. 補足・未確定

- 0x1a を WM8960 と**断定はしていない**(書込専用のため chip ID 読取り不可)。
  0x1a という定番コーデックアドレス + 8bit レジスタ + 読値不安定(=write-only)
  という状況証拠。回路図での確定が必要。
- 0x50 は EEPROM の公算(校正/設定データ?)。
- カーネル修正(mxs-saif の MCLK 改造等)は**不要**と判明(コーデック不在が主因)。

## 6. ツール(実機 /root、src/ にソース)

- `i2cack <bus> [addr]`(src/i2cack.c): アドレス ACK スキャン(レジスタ read 非依存)。
- `i2cread <bus> <addr> [n] [reg...]`(src/i2cread.c): 任意アドレスのレジスタ読取り。
- Nerves に `chmod`/`stat` 無し → `File.chmod(path, 0o755)` で実行権付与。
