# 起動時タッチ遅延 調査報告(プログラム側)

- 日付: 2026-09-04
- プロジェクト: hello_kiosk_brain(PW-SH6 / i.MX283 ARMv5 / 128MiB / Linux 6.1.70)
- 症状: **起動直後 5〜15 秒ほど、タッチの反応が遅延する**(ユーザー報告)。
- 方針: 実機充電中のためプログラム(コード)読解で原因を調査。

---

> **【解決 2026-09-05】真因は SSH デーモンの crypto/鍵初期化だった。**
> 下記「44MB NIF」仮説は**誤り**(.so を 2.66MB に縮小しても遅延は改善しなかった)。
> 実機トレースで確定した機序と修正は §7 を参照。SSH 起動を 25 秒遅延させるだけで
> 初回全画面描画が **13.2 秒 → 0.6 秒**、以降の毎秒描画も 108ms で安定。
> 修正コミット 1c2be01(ssh_daemon.ex)。

## 0. 結論(当初仮説 — 後日 §7 で否定)

**~~最有力原因 = 描画 NIF(`priv/kiosk_nif.so`)が 44MB もあり…~~**(誤り)
NIF サイズは無関係だった。以下 §1-§6 は当時の調査記録として残す。

**当時の修正**: リンクフラグ `-Wl,--gc-sections`(+ 各
`-ffunction-sections/-fdata-sections`)と `-s`(strip)を追加 → **44.7MB → 2.66MB
(94% 減)**。`.cpp` は無変更、IPA フォント保持。※起動時タッチ遅延には効かなかったが、
**常時メモリ(128MiB)と dlopen I/O の削減としては有効**なので残す価値あり。

## 1. タッチ入力経路(コード読解)

`Input`(GenServer)が spawn した reader プロセスが evdev(`/dev/input/event0/1`)を
blocking read し、デコードして `Kiosk`(GenServer)へ `{:touch,x,y}` を送る。
描画(`Native.render`)は dirty NIF(`ERL_NIF_DIRTY_JOB_CPU_BOUND`)。単一 ARMv5 コアの
ため、起動時に CPU が飽和すると reader/Input/Kiosk/描画が競合し、タッチが遅延する。

## 2. 起動時 CPU/遅延の寄与(ランク)

1. **44MB NIF の dlopen(最有力)**: `HelloKioskBrain.Native` は `@on_load` で
   `priv/kiosk_nif.so`(**44.7MB**)を load_nif する。これは Kiosk.init の
   `Native.init_display` 呼び出しで同期的に走る。44MB を SD から読む(数秒)+ mmap +
   ARMv5 の再配置 + 128MiB でのメモリ圧迫 → 起動を数秒ブロック。この間タッチは
   カーネルの evdev キューに溜まり、CPU が空いてから一気に処理される。
2. BEAM 起動 + モジュールロード(数秒、不可避)。
3. crng 初期化(~13 秒、SSH)。ただし SshDaemon は `handle_continue` で別プロセス化+
   リトライ設計で、待ちは CPU をあまり食わない(UI 非ブロック)。寄与は小。
4. 初回の全画面描画(dirty NIF)が単一コアを一時占有。
5. 毎 tick の `devmem` プロセス spawn(Pswitch/Battery)。起動時 CPU 飽和下では
   fork/exec が重いが、5〜15 秒規模ではない。

## 3. なぜ .so が 44MB か(原因の核心)

- `Makefile` の `LGFX_SOURCES` は `Fonts/efont/*.c` を wildcard で**全言語**含む:
  efont **ja 25MB / cn 17MB / kr 18MB / tw 33MB**(ソース計 ~93MB)。
- しかし NIF(`kiosk_nif.cpp` + `kiosk_draw.hpp`)が使うフォントは
  **IPA `fonts::lgfxJapanGothic_8〜40` と小型 `Font4` のみ**。**efont は完全に未使用**
  (efont を使うのは NIF に含まれない `gfx_test.cpp` だけ)。
- Makefile に `--gc-sections` が無いため、**未使用の efont データがリンク時に落ちず**
  .so に丸ごと残る。加えて debug_info 付き(未 strip)。→ 44MB。

## 4. 修正と検証(実機ビルドで size 確認済み)

`Makefile` に追加:
```
CXXFLAGS += ... -ffunction-sections -fdata-sections
LDFLAGS  += -shared -Wl,--gc-sections -s
```
効果(Bootlin armv5 で実ビルド):

| 版 | サイズ | 内容 |
|---|---|---|
| 旧 | **44,716,684 B (44.7MB)** | efont 全言語 + debug_info |
| 新 | **2,655,736 B (2.66MB)** | 未使用 efont 除去 + strip |

- 新 .so は **ARM 32bit ELF・NIF エントリ(`nif_init`)保持**。
- **使用中の IPA フォント 9 種(lgfxJapanGothic_8〜40)は保持**(nm で確認、.rodata
  2.58MB がフォント本体)。→ **日本語描画は壊れない**。
- `.cpp`/`.hpp` は無変更(papapa と同一のまま)。変更は Makefile のビルドフラグのみ。
- ※ `Makefile` の `CXX ?=` は Nerves/elixir_make が cross g++ を環境に入れるため
  正常に働く。手動 `make` 時のみ `make CXX=<toolchain>-g++` が必要(make 既定の
  `g++` が `?=` を上書きしホスト x86 を生むため)。

## 4.5 実機計測(2026-09-04、実機で確認)

小さい .so を実機に配備し計測:

| 項目 | 44MB(旧) | 2.66MB(新) |
|---|---|---|
| **.so の SD コールド読取り**(drop_caches 後 `cat > /dev/null`) | **3456 ms** | **324 ms** |

→ **起動時 dlopen の I/O が 3.5s → 0.3s(約11倍速、-3.1秒)**。dlopen はこの読取りに
加え mmap+ARMv5 再配置が乗るので実効削減はさらに大きい。128MiB でのメモリ圧迫も減。

- **再起動して小さい .so で起動 → Kiosk 正常・`Native.render`=:ok・日本語描画 OK**
  (IPA フォント保持を実画面で確認)。機能後退なし。
- 注: 「起動→Kiosk 準備」を SSH 経由で測ると crng(SSH 起動 ~十数秒)を含んでしまい
  タッチ準備の指標にならない。タッチ/UI は SSH より前に立つ。タッチ遅延の直接指標は
  上記「NIF ロードで Kiosk がブロックされる時間」= .so 読取り時間で、そこが 3.1秒短縮。

## 5. 次アクション(実機復帰後)

1. `mix compile`(elixir_make が新フラグで .so を再ビルド)→ release に 2.66MB .so。
2. デプロイ → **再起動して起動時タッチ遅延が改善するか実測**(これが本命の検証)。
3. 改善が不十分なら次候補: reader プロセスの `Process.flag(:priority, :high)`、
   毎 tick の devmem spawn 削減、初回描画の軽量化。まず①を測ってから。

## 6. 補足

- .so 縮小は起動時間だけでなく**常時のメモリ使用(128MiB)**にも効く(44MB→2.7MB)。
- efont が要る用途(中韓台フォント)が将来出たら、その言語だけ選択追加する。
  現状の日本語 KIOSK では IPA で十分。

## 7. 【解決】真因 = SSH デーモンの crypto 初期化(2026-09-05 実機トレースで確定)

### 計測方法
`Input` に heartbeat+reader トレース、`Kiosk.paint` に所要時間計測、描画 NIF
(`kiosk_nif.cpp`/`kiosk_draw.hpp`)に exec/blit/op 別計時を一時的に仕込み、
再起動して `/tmp/input_trace` を回収(計測コードは解決後すべて除去済み)。

### 決定的証拠
- **NIF 描画は速い**: `nifrender exec=86ms blit=37ms`(全画面 clear+text×39+blit)。
  op 別でも text 39 本で ~10-70ms。→ 描画処理自体は遅延の原因ではない。
- **paint の Elixir 側 wall は初回 13228ms**: NIF が 117ms しか使っていないのに
  `Native.render` 呼び出しが 13 秒かかる = **dirty NIF が単一コアの奪い合いで
  細切れにしか実行されず、13 秒かけてやっと 117ms 分を消化**していた。
- **単一コア確定**: `logical=1, schedulers=1, dirty_cpu=1`。起動中 BEAM CPU ~97%。
- **SSH 起動時刻とペイント収束が一致**: SSH ポート応答が BEAM init から ~55 秒後、
  ペイント収束(paint 13.2s→0.1s台)も ~45-58 秒。
- **決定実験**: `SshDaemon` の daemon 起動を 30 秒遅延 → 再起動計測で
  **paint 0 が 13228ms → 613ms、paint 1 以降は 108ms**。SSH を後ろにずらしただけで
  起動時タッチ遅延が消滅 = **SSH crypto/鍵初期化が真犯人**と確定。

### 機序
`SshDaemon` は supervision tree で Kiosk より前に起動し、`:ssh.daemon` の
crypto/host-key 初期化が ARMv5 単一コアを起動直後の数十秒ほぼ 100% 占有する。
その間、描画 dirty NIF とタッチイベント処理(reader→Input→Kiosk)が CPU 飢餓に
陥り、ユーザーには「画面は出ているがタッチが ~25 秒効かない」と見える。

### 修正(コミット 1c2be01)
`SshDaemon.init` で daemon 起動を `Process.send_after(:try_start_delayed, 25_000)`
に変更(handle_continue 即時起動をやめる)。crng 待ちのリトライ設計は維持。
SSH はヘッドレス保守用途で数十秒の遅延に実害なし。UI は起動直後から即応答。

### 補足
- §0-§6 の「44MB NIF」修正(2.66MB 化)は起動時タッチ遅延には無効だったが、
  常時メモリと dlopen I/O 削減としては有効なので維持。
- さらに詰めるなら: SSH 遅延時間の調整、あるいは crng seed 同様に SSH 前段の
  crypto を軽くする案。現状 25 秒で実用十分。→ **後日さらに真因が判明(§8)**。

## 8. 【最終解決】"SSH crypto 初期化" の正体 = user_passwords の PBKDF2(2026-09-05)

§7 の「25 秒遅延」は対症療法で、遅延ユーザー報告「38 秒〜1 分 20 秒でタッチ遅延」=
**負荷が後ろへ移動しただけ**だった。フェーズ計測+スタックサンプリングで真因を確定。

### 計測(実機、ssh_daemon.ex に一時計測を仕込み再起動1回)
```
try_start 開始     VM+34.0s (=遅延25s後)
モジュール遅延ロード crypto 0.7s / public_key 3.5s / ssh 1.7s ≈ 計6s
:crypto.strong_rand_bytes(32) = 4ms  (crypto 自体は速い)
:ssh.daemon(22, opts)         = 37.5s ←★ ここがほぼ全部
```
- アイドル状態で 2 個目のデーモンを起てても **35.4s** → 起動時競合ではなく恒常的。
- 起動中のスタックを 0.5s 毎サンプリング → **`:crypto.pbkdf2_hmac/5`**(70 サンプル中70)。
  呼出し元は `:ssh_options.make_passwd_fun/1` と `:ssh_options.maybe_add_fake_passwd_checker/2`。

### 機序
- `user_passwords: [{~c"user", ~c"brain"}]` を渡すと、OTP の ssh はデーモン起動時に
  パスワードを **PBKDF2**(意図的に遅い KDF)でハッシュ化し、さらにユーザー列挙の
  タイミング攻撃対策で**ダミーチェッカー用にもう 1 回** PBKDF2 を回す。
  ARMv5 @454MHz では **計 35 秒**。
- PBKDF2 は dirty CPU NIF のため、**唯一の dirty CPU スケジューラ(dirty_cpu=1)を
  占有**し、描画 NIF(dirty)がその後ろに並ぶ = タッチ/描画の飢餓。§7 の
  「初回描画 13.2 秒」も同根(SSH 即時起動時代は PBKDF2 が起動直後に走っていた)。
- crng は無関係(kernel 6.1 は jitter entropy で **起動 3.3 秒で crng init done**。
  dmesg 実測)。moduledoc の「crng に数分」は旧カーネルの知識で現行では成立しない。

### 修正(実測値つき)
1. **`user_passwords` → `pwdfun`(自前の平文比較)**: pwdfun を渡すと PBKDF2 経路を
   通らない。`:ssh.daemon` **35.4s → 0.106s**(330 倍)。鍵認証・パスワード認証
   (user/brain)とも動作確認済み(ループバック `:ssh.connect` で password 認証成功)。
2. **ssh 系モジュールの遅延ロード(SD 読み 計約 6s)を 15ms 間隔の逐次事前ロード**に
   分散(単発 0.1-0.5s のロード塊でタッチが詰まらないように)。
3. **起動遅延 25s → 10s**。SSH は従来の電源+約 90 秒 → **約 40 秒早く**利用可能に。

### 検証
- 再起動後、ホストから reboot 発行 +50s で SSH ポート応答(シャットダウン込み)。
- ユーザー実機確認: 旧 38s〜80s の遅延帯は解消。**30〜40s に軽微な引っかかり**
  (=モジュール事前ロードの帯、単発 0.1-0.5s)が残るが**利用上問題なし**。
- 教訓: 「SSH crypto/鍵初期化が重い」で止めず内訳まで割ると、遅延(=移動)ではなく
  **除去**できた。ARMv5 級の単一コアでは `user_passwords` は使ってはならない。
