# セカンドオピニオン質問書：ONKYO UWF-1(AR9271)が i.MX28 USB ホストをハングさせる

- 日付: 2026-09-06
- プロジェクト: hello_kiosk_brain(SHARP Brain PW-SH6 / i.MX283 ARMv5 / 128MiB / Linux 6.1.70)
- 目的: USB WiFi 化の一環で **ONKYO UWF-1(Atheros AR9271, `0cf3:9271`, ath9k_htc)** を接続すると
  システムがハングする現象について、切り分けの**矛盾点**を洗い出し、第三者の意見を求める。
- 起票理由: 起票者(担当+AI アシスタント)の切り分けに、以下に列挙する**論理的矛盾・未検証の飛躍**が
  あるため、鵜呑みにせず外部知見で再検証したい。

---

## 1. 環境・構成(事実)

- 稼働カーネル: **`6.1.70-ga9f534c7f53e-dirty`**(brain-hackers linux-brain の 6.1 ブランチを
  自前で再ビルド。パッチ2点: ①ath9k `hif_usb.c` の endpoint 検査ブロックを削除、
  ②`CONFIG_BT`/`BT_HCIBTUSB`=y 追加)。ツールチェーンは Bootlin arm-linux-gcc 14.3.0。
- USB: i.MX28 `ci_hdrc.0`。dmesg で **`USB 2.0 started, EHCI 1.00`**(ホストは高速=HS 対応)。
  microUSB → OTG → **セルフパワー USB ハブ** → 子機群、という構成(USB ホスト化は有線LANで実績あり)。
- 接続機器(ハブ配下): **UWF-1(AR9271, `0cf3:9271`)** と **USB-Ethernet(`1a86:e396`, 10/100)**。
- UWF-1 の firmware: `htc_9271-1.4.0.fw`(**51008 バイト、kernel.org linux-firmware の正規版**、md5
  `c5b2dc29f7ec2f053169ada3b2ef70ae`)を `/lib/firmware/htc_9271.fw` と
  `/lib/firmware/ath9k_htc/htc_9271-1.4.0.fw` に配置済(カーネルマウントで確定配置、md5 一致確認済)。
- 補足: 全 USB デバイスに **`not running at top speed; connect to a high speed hub`** が出る
  (= 実効フルスピード動作)。ただし **USB-Ethernet はフルスピードでも正常動作**(eth0 で DHCP 取得・
  SSH 稼働)。

## 2. ath9k endpoint 検査パッチ(前提)

6.1 の `ath9k_hif_usb_probe` は endpoint 検査で UWF-1 を弾いていた(REG_OUT を interrupt-OUT として
要求、UWF-1 は該当エンドポイントが bulk・interrupt-OUT 無し → `-ENODEV`)。5.15 未満では動いていた
デバイスなので、**検査ブロックと未使用変数を削除**して pre-5.15 挙動に戻した。結果、検査は通過し、
ドライバは firmware 転送段階まで到達するようになった(下記の観察はすべてこのパッチ適用後)。

## 3. 観察された事実(再現あり)

| # | 操作 | 結果 |
|---|---|---|
| A | **UWF-1 を挿したまま起動** | コンソールが `usb 1-1.3: ath9k_htc: transferred FW ... size:51008` で停止。KIOSK 出ず・ネットワーク不通 |
| B | **UWF-1 を外して起動** | KIOSK 正常・eth0=DHCP(192.168.222.57)・**Bluetooth スタック初期化成功**。健全 |
| C | Bで健全起動後 **UWF-1 をホットプラグ(1回目)** | ping/eth0 停止。**UWF-1 を抜くと eth0 復活**(KIOSK に IP 再表示、SSH 可) |
| D | 再度 **UWF-1 をホットプラグ(2回目)** | ping 停止。**UWF-1 を抜いても復帰せず**、KIOSK は稼働秒数 `3:13` で凍結(=システム全体ハング)。電源リセットが必要 |

- B の dmesg 抜粋(健全時): `Bluetooth: Core ver 2.22` / `NET: Registered PF_BLUETOOTH` /
  `HCI device and connection manager initialized` / `ci_hdrc.0: USB 2.0 started, EHCI 1.00`。
- **A/D のハング時 dmesg は未取得**(A はコンソール以外に出力経路なし、D はハングして SSH 不能・
  次回起動で ring buffer は消える)。ここが最大の情報欠落。

## 4. 起票者の暫定解釈と、その【矛盾点】

暫定的に「AR9271 がこの USB 経路(フルスピード)でリセット/初期化に失敗し、USB ホストを wedge、
ひいてはシステムをハング」と説明したが、以下の矛盾・飛躍がある:

1. **【矛盾1】async firmware load がなぜ boot/システムをブロックするのか**
   `ath9k_hif_usb_probe` は `request_firmware_nowait`(非同期コールバック)で firmware を要求する。
   本来 probe は即 return し boot をブロックしないはず。にもかかわらず観察 A では
   `transferred FW` で**コンソールが停止**した。非同期のはずが同期的にブロックして見える理由が不明。
   (probe が `hif_dev->fw_done` の completion を待つ経路がある? USB 列挙スレッドが専有される?
   単にコンソール最終行がそれだっただけで実際は別要因?)

2. **【矛盾2】フルスピード説が USB-Ethernet の動作と両立しない**
   「AR9271 は HS 前提でフルスピードだから失敗」と述べたが、**同じハブ配下の USB-Ethernet は
   フルスピードで正常動作**している。かつ **ホスト(ci_hdrc)は EHCI/USB2.0 で HS 対応**と出ている。
   よって「フルスピードだから」は AR9271 固有の失敗を説明できていない。そもそも何がフルスピードを
   強制しているか(ハブが USB1.1 か、OTG ケーブル/PHY か)も未確認。

3. **【矛盾3】復帰の不一致(USB wedge か / ハードハングか)**
   観察 C(1回目)は抜くと eth0 復活=USB レベルの回復可能な wedge。観察 D(2回目)は抜いても復帰
   せず=システム全体のハードハング。**同一デバイス・同一操作で重症度が違う**。この非決定性の説明が
   ない(初期化の競合状態? メモリ 128MiB の枯渇? 電源?)。

4. **【未検証の代替仮説】電源(電流)起因の可能性を排除できていない**
   AR9271 は TX/初期化時の消費電流が大きい。セルフパワーハブでも、i.MX28 の VBUS 経路や自身の電源
   レールがブラウンアウトすると SoC ごとハングしうる(本機は「5V が来れば必ず起動」等、電源に
   敏感なシリコン特性がある)。USB プロトコル層の問題か、電源(電流)の問題かを切り分けていない。

## 5. 質問(セカンドオピニオンを求めたい点)

1. **観察 A/D のハング機序**: `ath9k_htc` の firmware ダウンロード〜デバイス再列挙
   (`transferred FW` 後にデバイスが disconnect→reconnect する既知シーケンス)が、i.MX28
   `ci_hdrc` 上で **boot スレッド or システム全体をハングさせる**のは、どの層の問題として典型的か
   (USB core の同期 probe / hub thread 専有 / ci_hdrc の IRQ・DMA デッドロック / 電源)。
   非同期 firmware load が実質同期ブロックに見える理由の説明を求む。

2. **フルスピード強制の原因と是非**: `not running at top speed` を出しつつ USB-Ethernet は動く。
   何が HS 交渉を阻んでいるか(セルフパワーハブが USB1.1 の可能性 / OTG ケーブル結線 / i.MX28
   USB PHY 設定)。**HS 対応の USB2.0 ハブや別ケーブルに替えれば AR9271 が安定する**見込みはあるか。

3. **電源 vs プロトコル の切り分け方**: ハング時の dmesg が取れない中で、AR9271 のハングが電流
   ブラウンアウト起因かプロトコル起因かを、非破壊で切り分ける実務手順(電池ログの mV 監視、別電源
   ハブ、電流計測、`usbcore.old_scheme_first`/`authorized` 制御、`ath9k_htc` の module param 等)。

4. **回避手段の有無**: この AR9271 を i.MX28/ci_hdrc/6.1 で安定動作させる **ath9k_htc / ci_hdrc の
   quirk・module param・DT 設定**は存在するか(例: NAK/reset 抑制、endpoint 再検査、`dr_mode`/
   `maximum-speed` の DT 指定、`ci_hdrc` の `phy_type`・`itc-setting` 等)。それとも AR9271 は
   この構成では実務上不可で、**MediaTek MT7601U/MT7610U 等のフルスピード耐性のある別チップに
   替えるのが妥当**か。

5. **切り分けの妥当性**: §4 の矛盾を踏まえ、「AR9271 固有の非互換」という結論自体が早計で、
   実は**ハブ/ケーブル/電源といった周辺要因**の可能性はどれくらいあるか。次に取るべき最小実験は何か
   (例: UWF-1 を別 HS ハブ単独 + 外部給電で・USB-Ethernet 無しで挿し、ハング時に
   `dmesg -w` を別コンソール[SSH over usb0 gadget に一時退避]で採取する等)。

## 7. 【決定的検証結果】(2026-09-06、セカンドオピニオン TEST2 実施)

セカンドオピニオンの助言に従い、UWF-1 を**母艦(AlmaLinux, kernel 6.12.0, x86)**に挿して
`lsusb -v -d 0cf3:9271` と動作を確認した。結論は**私の切り分けの複数を棄却**する。

### (A) UWF-1 のエンドポイントは正しい(0x04 は Interrupt OUT)
`lsusb -v` の Endpoint Descriptor:
```
0x01 OUT  Bulk      512B   (WLAN_TX=1) ✓
0x82 IN   Bulk      512B   (WLAN_RX=2) ✓
0x83 IN   Interrupt  64B   (REG_IN=3)  ✓
0x04 OUT  Interrupt  64B   (REG_OUT=4) ✓   ← Interrupt OUT。ath9k_htc の要求と一致
0x05 OUT  Bulk      512B
0x06 OUT  Bulk      512B
```
→ **§4 と §2 で「0x04 は bulk・interrupt-OUT 無し」と書いたのは誤読**(Brain の sysfs 読みが
誤り)。実際は **REG_OUT=0x04 は Interrupt OUT** で、ath9k_htc(WLAN=bulk / REG=interrupt)の
期待構成に完全一致する。**→ endpoint 検査は本来 UWF-1 を通すべき。**

### (B) UWF-1 は母艦で正常動作(本物の AR9271)
母艦で `ath9k_htc` がバインドし **`wlp0s20f0u1`(USB WiFi インタフェース)を生成**。
= **UWF-1 は欠陥のない、正常動作する AR9271**。

### (C) 棄却された仮説
- **「endpoint 不一致で URB type mismatch → ハング」= 棄却**(エンドポイントは正しい)。
- **「フルスピードだから AR9271 が動かない」= 棄却**(母艦でも当該デバイスは動く。かつ FS の
  AR9271 動作例あり)。
- **§2 の endpoint パッチの前提(REG_OUT が bulk)も誤り**。パッチ自体は「検査を消す」ものだが、
  そもそも検査は通るべきで、削除は不要だった可能性が高い。

### (D) 残る真因 = i.MX28 `ci_hdrc` × AR9271(セカンドオピニオン仮説②)
UWF-1 は正常品・エンドポイント正常・母艦で動作。にもかかわらず **Brain(i.MX28, 6.1.70)では**
①stock カーネルが endpoint 検査で mis-reject し、②検査を消すと firmware 転送後にシステムハング。
→ 問題は **i.MX28 の ci_hdrc USB ホストと AR9271 の複雑な USB シーケンス
(firmware download → デバイス再列挙 → HTC/WMI 初期化)の相互作用**に絞られた。
USB-Ethernet(単純な USB 動作)は同じ経路で動くが、AR9271 の再列挙/HTC を i.MX28 が捌けていない疑い。
(なお Brain stock の endpoint mis-reject 自体、i.MX28 経路での descriptor 読取りの不安定さの
現れである可能性もある=同根の症状かもしれない。)

### (E) 次の実務判断
- **カーネル**: endpoint パッチは前提が誤りだったので**復元**(stock ath9k に戻す)し、**CONFIG_BT
  は保持**して再ビルドするのが安全な着地(stock 検査が UWF-1 を firmware 前に弾く=**ハングを回避**、
  かつ BLE 用 BT は残る)。UWF-1 の WiFi を Brain で使うには i.MX28×AR9271 のハング解明が別途必要。
- **ハング解明の要**: Brain でハング時の dmesg を残す手段(ramoops/pstore/UART)。SSH は死ぬので不可。
- **代替**: WiFi は AR9271 の複雑シーケンスを避け、より単純な MediaTek MT7601U 等を試す価値。
  ただし「i.MX28×AR9271」の相性問題であって「AR9271 一般が不可」ではない点を明確化した。

## 8. 【根本原因の確定】ハブが Full-Speed 接続(2026-09-06)

セカンドオピニオン助言(Brain の descriptor を母艦と突合)を実施し、**真因を特定**した。

### (A) Brain と母艦で descriptor の読み取りが違う
安全カーネル(検査復元)で UWF-1 を Brain に挿し(検査で弾かれるが列挙はされる)、
`/sys/bus/usb/devices/1-1.3:1.0/ep_*/` を読んだ:

| EP | 母艦(lsusb -v) | **Brain(sysfs)** |
|---|---|---|
| 0x04 | Interrupt, 64B | **Bulk, 64B** |
| 0x01 (bulk) | Bulk, **512B** | Bulk, **64B** |
| 0x82 (bulk) | Bulk, 512B | Bulk, **64B** |
| 0x83 (int) | Interrupt, 64B | Interrupt, 64B |

Brain は全 bulk を **64B**(母艦は 512B)、**0x04 を Bulk**(母艦は Interrupt)と読む。
= **典型的な Full-Speed 時のエンドポイント記述**(USB bulk は HS=512B / FS=64B)。

### (B) 接続速度を確認 → ハブが Full-Speed
`/sys/bus/usb/devices/*/speed`:
```
usb1  (i.MX28 root/EHCI)   speed=480   High-Speed ✓
1-1   (hub 0a05:7211)      speed=12    ★Full-Speed(USB2.0ハブなのに FS で接続)
1-1.3 (UWF-1)              speed=12    FS(ハブ配下)
1-1.4 (USB-Ethernet)      speed=12    FS(ハブ配下)
```
**ハブ自身が HS ルートに対して Full-Speed で接続**しており、配下の全デバイスが FS になる。

### (C) 真因(確定)= HS negotiation 失敗(ハブ/ケーブル/信号品質)
- AR9271 は FS 接続時に **FS 用 descriptor(0x04=bulk, 64B)** を提示。これは ath9k_htc の期待
  (HS descriptor: 0x04=interrupt, bulk=512B)と食い違うため、**endpoint 検査が正しく弾く**。
  検査を削除して無理に通すと、誤ったエンドポイント種別/サイズで URB を組み、AR9271 の
  firmware 後シーケンスでハング。
- 母艦は UWF-1 を **直挿し=HS** で繋ぐため正しい descriptor を取得し正常動作。
- → **AR9271/UWF-1 は正常。i.MX28 との相性問題でもない。真因は「microUSB→OTG→ハブ の経路が
  High-Speed で繋がらず Full-Speed に落ちる」こと**(セカンドオピニオン仮説③=ハブ/ケーブルが的中)。
  なお §3 の観察 A(起動時ハング)・§4 の矛盾(FS 説と Ethernet 動作の両立)も、これで一貫説明できる
  (Ethernet は FS でも動く単純デバイス、AR9271 は HS descriptor 前提なので FS で破綻)。

### (D) WiFi 開通の道
**Brain の USB を High-Speed で接続できれば UWF-1 は動く**見込み。対策:
1. **短く良質な OTG ケーブル + 別の USB2.0 ハブ**(HS chirp が通るもの)に交換 ← 最有力・最簡単。
   交換後 `/sys/bus/usb/devices/1-1/speed` が **480** になれば成功。
2. i.MX28 USB PHY チューニング(DTB の usbphy tx/rx 設定)。
3. HS 信号を阻む要因(ケーブル結線・アダプタ)の除去。

### (E) カーネル方針(確定)
**endpoint 検査は復元が正解**(FS descriptor を正しく弾き、ハングを防ぐ)。CONFIG_BT は保持。
= 現在の安全カーネル(`zImage-6.1.70-bt-safe`)を常用ベースにする。UWF-1 の WiFi は「USB を HS に
する」ハード対策が付いてから再挑戦(カーネルは変更不要で動くはず)。
