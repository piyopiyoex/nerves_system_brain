## ★ 第1回セカンドオピニオンの要点（2026-09-03 受領・反映済み）

1. **`entropy_avail >= 128` 待ちは CRNG readiness の判定として誤り**。
   entropy_avail は pool 推定値で、crng_ready() とは別物。
   → `getrandom(…, GRND_NONBLOCK)` で成功/EAGAIN を見て直接判定すべき。
   **今回の「4分待っても開通せず」の直接原因はこれの可能性大**（crng は
   ready なのに entropy_avail が 128 に届かず永久待ち）。
2. **i.MX28 DCP は Linux 上では AES/SHA アクセラレータ**であり、
   HWRNG ドライバとしては登録されない見込み。「DCP=HWRNG」を前提に
   カーネル再ビルドへ進む前に要確認（`CONFIG_CRYPTO_DEV_MXS_DCP` は crypto であって hwrng ではない）。
3. **対策の優先順位**: ① persistent random seed（本命）→ ② U-Boot が
   `/chosen/rng-seed` を生成 → ③ 実在する HWRNG の確認 → ④ jitterentropy →
   ⑤ アプリ側回避（getrandom を /dev/urandom へ・GRND_INSECURE 等は**非推奨**）。
   `random.trust_cpu=on` は ARMv5 に CPU RNG が無いので無意味。
   `random.trust_bootloader=on` は seed が実在する場合のみ有効。
   `rngd`/`haveged` は HWRNG か jitterentropy の source が無いと無力。

### この回答を受けた実機調査結果（2026-09-03）

- **ブート DTB の `/chosen` は空**（`rng-seed` プロパティ無し）
  → 現状 U-Boot は bootloader seed を渡していない。②案は U-Boot 側対応が前提。
- 手元の起動時 dmesg（起動30秒時点）には crng/hwrng/jitter 関連行が
  `Initialise system trusted keyrings` 以外に見当たらない
  → 実機の `/proc/config.gz` とフル dmesg（crng init done を含む）を SD 経由で取得予定。
- **方針転換**: まず ①(persistent seed) を本命に据える。当面の即効策として
  「entropy_avail 待ちを廃止し、`:crypto.strong_rand_bytes` の初回ブロックが
  解ける時刻（＝ crng ready 時刻）を実機で実測」して、crng が確実に来るか・
  何秒かを確定させる。来るなら persistent seed で初回待ちを潰す。

## 0. 要約（3行）

- カスタム Nerves システム上で Elixir アプリ（KIOSK 表示 + OTP 組み込み `:ssh` デーモン）を動かしている。
- **`:ssh.daemon/2` を呼ぶ手前の `:crypto.strong_rand_bytes/1` がブロックし、SSH が起動しない**。原因は ARMv5 実機の **crng(乱数)初期化がエントロピー枯渇で数分〜完了しない**こと。
- エントロピー待ちループを入れたが 4 分待っても開通せず。**この機種で SSH(と crypto 全般)を実用的に起動する定石**を知りたい。

## 1. ハードウェア / ソフトウェア構成

| 項目 | 内容 |
|---|---|
| 実機 | SHARP Brain PW-SH6（電子辞書） |
| SoC | NXP i.MX283（ARM926EJ-S, **ARMv5TEJ**, soft-float, 454MHz） |
| RAM | 128 MiB |
| カーネル | Linux 6.1.70 armv5tejl（brain-hackers/linux-brain, 2026-03-24ビルド。**モノリシック、/lib/modules 無し**） |
| ディスプレイ | braindrmfb（brain-hackers 製 DRM ドライバ）、854×480 RGB565 |
| ネットワーク | **USB Ethernet Gadget (NCM) のみ**。WiFi/有線なし。母艦 10.42.0.1 ⇔ Brain 10.42.0.2 |
| Nerves システム | 自作 `nerves_system_brain`（nerves_system_br v1.34.3 / Buildroot 2026.05.2 / Bootlin armv5 glibc ツールチェーン / **カーネル・U-Boot・DTB は brain-hackers 資産を流用**、Buildroot ではビルドしない / rootfs は **ext4**、squashfs 非対応） |

補足：ここに至るまで、直接SDブート・USB-NCM・OTP/Elixir 実機動作・フレームバッファ描画・アプリの完全リモート開発サイクル（SFTP + ホットリロード + fbダンプによるスクリーンショット）は**すべて確立済み**。唯一 SSH デーモンの起動だけが未解決。

## 2. 症状と切り分けの経緯（時系列）

Brain は RTC を持たず全ファイルのタイムスタンプが 1970 になるため、ログファイルへの
段階出力（同期フラッシュ付き）で切り分けた。SshDaemon の `init`/`handle_continue` に
ステップログを仕込んだ結果：

```
init start
start crypto => {:ok, []}
start asn1 => {:ok, []}
start public_key => {:ok, []}
start ssh => {:ok, []}
        ← ここで停止。この次の :crypto.strong_rand_bytes(4) が返ってこない
```

- **BEAM はクラッシュしていない**（erl_crash.dump は生成されない。ping も通り続ける）。
  `:crypto.strong_rand_bytes/1` の呼び出しが**ブロックしたまま**。
- 以前の素の起動ログでは、カーネルの `random: crng init done` が**起動後 160〜250 秒**に出ていた
  （キーボード・タッチ等の割り込みが乏しく、エントロピー蓄積が非常に遅い）。
- → **crng 未初期化により getrandom(2)（= OpenSSL 経由の strong_rand_bytes）がブロック**、と判断。

### 打った対策と結果

**対策A：エントロピー待ちループ**（`/proc/sys/kernel/random/entropy_avail` が 128 以上になるまで
1秒ポーリングしてから daemon を起動）。Display(KIOSK 表示)は先に起動する構成に変更。

→ **結果：4分待っても SSH 開通せず**（ping は通る＝BEAM 生存）。`entropy_avail` が
128 に到達していない可能性が高い（現在ログ確認中）。

## 3. 確定している事実

1. `:crypto` アプリ自体の起動は成功する（`ensure_all_started(:crypto) => {:ok, []}`）。
2. しかし `:crypto.strong_rand_bytes/1` は crng 初期化前だとブロックする。
3. カーネルログに `random: crng init done` が出るのは起動後 2.5〜4 分（割り込み源が乏しい）。
4. SSH ホスト鍵は事前生成済みファイル（priv/ssh に同梱）で、鍵生成自体は不要。
   ブロックしているのは crypto の乱数取得そのもの。
5. カーネルはモノリシック（モジュール追加不可）。dmesg には hwrng / jitterentropy の
   明示ログは未確認（`crng init` 関連以外に rng らしき行が見当たらない）。
6. この Brain 用カーネルは brain-hackers 製で、こちらでの再ビルドは可能だが重い工程。

## 4. 質問（セカンドオピニオンを求めたい点）

**主質問：ARMv5 / Linux 6.1 / エントロピー枯渇の組込み機で、OTP 29 の `:ssh`(および crypto 全般)を
起動時に確実かつ短時間で動かす定石は何か？** 具体的に、以下のどれが最善か、他に定石があるか。

1. **カーネルコマンドラインで crng を信頼させる**
   - `random.trust_cpu=on` / `random.trust_bootloader=on` は ARMv5 で意味があるか？
   - U-Boot の bootargs にシード（`random.seed=...` 等）を渡す方法は現実的か？
2. **ハードウェア RNG を使う**
   - i.MX28 は DCP(Data Co-Processor) に RNG を持つはず。これを DTB/カーネル config で
     `hwrng` として有効化し、crng を即 seed するのが正攻法か？ その場合の最小手順は？
3. **jitterentropy / haveged 相当**
   - カーネルの `CONFIG_RANDOM_TRUST_CPU` 系や jitterentropy-rng を有効化して
     再ビルドするのが妥当か？ Buildroot 側で haveged パッケージを足す手はどうか？
4. **エントロピーを人為注入**
   - 起動時に `/dev/urandom` を読む/CPU を回す程度では credit されない認識だが、
     `rngd`(rng-tools) を rootfs に入れて動かすのが実務的な最短か？
     nerves_system_br にはかつて rng-tools を自動選択していた歴史があるはずで、
     それを踏襲すべきか？
5. **アプリ側で回避**
   - OTP/OpenSSL の乱数ソースを getrandom ブロッキングでなく `/dev/urandom`（非ブロッキング）に
     向ける方法はあるか？ セキュリティ上の許容範囲込みで。
   - `:crypto` の RAND を差し替える、`GRND_INSECURE` 相当を使う等の現実解は？
6. **そもそもの設計**
   - 起動直後の SSH 到達性が要件（開発利便性）。crng 完了まで数分待つのは許容できるが、
     4分でも開通しないのは想定外。エントロピー待ちの実装自体に落とし穴はないか
     （`entropy_avail` の閾値、`getrandom` の GRND_RANDOM vs デフォルトの差など）。

## 5. 参考：現在の SshDaemon 実装（要点）

```elixir
def handle_continue(:start_daemon, state) do
  for app <- [:crypto, :asn1, :public_key, :ssh],
    do: Application.ensure_all_started(app)

  wait_for_entropy()               # /proc/.../entropy_avail >= 128 を1秒ポーリング(最大600s)
  :crypto.strong_rand_bytes(4)     # ← crng 未初期化だとここでブロック

  system_dir = :code.priv_dir(:hello_kiosk_brain) |> Path.join("ssh") |> String.to_charlist()
  sftp = :ssh_sftpd.subsystem_spec(cwd: ~c"/", root: ~c"/")
  :ssh.daemon(22, [
    system_dir: system_dir, user_dir: system_dir,
    user_passwords: [{~c"user", ~c"brain"}],
    shell: fn _u,_p -> spawn(fn -> IEx.Server.run([]) end) end,
    exec: {:direct, &eval/1},
    subsystems: [sftp]
  ])
end
```

（Display と SSH は独立の子プロセス。Display=KIOSK 表示は起動しており、SSH のみブロック中。）

## 6. 制約・前提

- ネットワークは USB-NCM のみ。SSH が唯一のリモート手段だが、初回配備・障害時は
  SD カードの物理差し替えで対応できる（実績あり）。
- カーネル再ビルドは可能だが避けたい（brain-hackers 資産の pin を崩したくない）。
  ただし RNG のためなら DTB/config の最小変更は許容範囲。
- ネットワーク経由の秘匿性はローカル 1:1 リンクのため脅威モデルは緩い。
  ただし乱数品質を落とす回避策の場合、その妥当性の意見も欲しい。
