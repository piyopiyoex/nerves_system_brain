# セカンドオピニオン質問書(第2弾)：i.MX28 USB ホストが High-Speed にならない原因の切り分け

- 日付: 2026-09-06
- プロジェクト: hello_kiosk_brain(SHARP Brain PW-SH6 / i.MX283 ARMv5 / Linux 6.1.70)
- 前提: [20260906_UWF1_AR9271_USBハング_セカンドオピニオン質問書.md](20260906_UWF1_AR9271_USBハング_セカンドオピニオン質問書.md)
  の調査(前回のセカンドオピニオン=「Brain と母艦で descriptor を突合せよ」が決定打。感謝)。
- 本書の目的: **i.MX28 の USB リンクが High-Speed(480Mbps)で確立しない原因を、AR9271/ath9k_htc から
  切り離して特定する**こと。

> ⚠ 用語の厳密化(前回の言い過ぎを訂正): 前回「真因はハブが Full-Speed だから」と書いたが、これは
> **言い過ぎ**。正確には下記の【確定】と【未確定】を分ける。

---

## 1. 【確定】と【未確定】

### 確定した事実
1. **UWF-1(AR9271, 0cf3:9271)は正常なデバイス**。母艦(x86, kernel 6.12)に**直挿し=HS**で繋ぐと
   `ath9k_htc` がバインドし `wlp0s20f0u1` を生成、正常動作。
2. **Brain 上では当該 USB リンクが Full-Speed(12Mbps)で確立している**
   (`/sys/bus/usb/devices/1-1/speed = 12`)。
3. **FS 接続では AR9271 が使えない**:FS 時、AR9271 は 512B バルクを提示できず(FS 上限 64B)、
   0x04 も別種別になる。この FS descriptor が ath9k_htc(HS 前提)と食い違い、endpoint 検査で
   正しく弾かれる/検査を外して無理に通すと firmware 後シーケンスでハングする。
   - Brain sysfs(FS): `0x04=Bulk/64B`, bulk=`64B` ⇔ 母艦 lsusb(HS): `0x04=Interrupt/64B`, bulk=`512B`。

### まだ未確定(本書の主題)
- **なぜ Brain の USB リンクが Full-Speed でしか確立しないのか**。
  経路は多段: **i.MX28 USB PHY → microUSB コネクタ → microUSB-OTG 変換 → USB ケーブル →
  ハブ upstream PHY**。この**どの要素**(PHY 較正 / OTG 変換 / ケーブル品質 / ハブ個体・相性)で
  HS negotiation(chirp)が失敗しているかは**特定できていない**。
- 「0a05:7211(ver=2.00 表示)」は HS 対応のはずだが、**HS 対応ハブでも upstream リンクが FS で
  確立している**のは、ハブ単体の問題とは限らず、i.MX28↔ハブ間リンクの問題である可能性が高い。

→ 本件は「AR9271 を動かすための HS 化」ではなく、**「i.MX28 USB 経路が正常な USB2.0 HS リンクを
成立させられるか」を AR9271 と独立に検証する**問題として扱う(問題の下流への移動=良い進展だが、
科学的にはここで一段止めて原因を特定すべき)。

## 2. 物理構成

- 経路: **PW-SH6 microUSB → microUSB-OTG 変換 → USB ケーブル → セルフパワー USB ハブ(0a05:7211)
  → 子機**。
- i.MX28 USB0(`usb@80080000`, ci_hdrc)は DTB で `dr_mode = "host"`。ホストは EHCI で
  `USB 2.0 started`、root(`usb1`)=480Mbps は出ている(=**ホスト側 HS は生きている**)。
- DTS に i.MX28 usbphy(`usbphy@8007c000` 等, `fsl,imx28-usbphy`)あり。
- 電源はセルフパワーハブから(USB ホスト化・有線LAN は FS で安定動作の実績)。

## 3. 段階検証プラン(この順で原因を AR9271 から切り離す)

セカンドオピニオン助言に沿い、**PHY レジスタ調整より先にハードウェア経路を固定・切り分ける**。

| Stage | 実験 | 判定 |
|---|---|---|
| **0** | 現状: ハブ配下に UWF-1+Ethernet、`1-1/speed=12` | 既知 |
| **1** | **ハブ単体**(子機なし)を Brain に接続し `1-1/speed` を見る※ | 12 のまま → AR9271 は完全に無関係と確定。以降 OTG/ケーブル/ハブ/PHY のみを調査 |
| **2** | **HS 対応 USB2.0 メモリを(ハブ経由 or 直結で)接続** | メモリ=480 なら i.MX28 PHY+OTG 経路は HS 可能→**ハブ/相性**が疑い。メモリ=12 なら**物理経路(OTG/ケーブル/PHY)**が疑い |
| **3** | **交換マトリクス**(OTG 変換 / ケーブル / ハブ を1つずつ別品に) | どれを替えると 480 になるかで犯人を一意特定 |
| **4** | HS 成立後に UWF-1 → `1-1.3/speed=480`・512B descriptor | ここで初めて AR9271 の HS 動作を検証 |
| **5** | ath9k_htc → firmware → wlan interface | WiFi 開通 |

※Stage1 の注意: 子機を全部外すと Brain のネットワーク(eth0)も無くなり SSH で `speed` を読めない。
そのため実務上は「**Ethernet だけ残して UWF-1 を外す**」で `1-1/speed` を観測する(ハブ upstream の
速度は子機構成に依らないはずなので、これで十分ハブリンク速度を確認できる)。より厳密には UART/
シリアルコンソールがあればハブ単体で観測できるが、PW-SH6 は UART が容易でない。

### 交換マトリクスの例(OTG × ケーブル × ハブ)
```
OTG  Cable  Hub  → speed
 A    A     A    → 12   (現状)
 B    A     A    → ?    (OTG変換を替える)
 A    B     A    → ?    (ケーブルを替える)
 A    A     B    → ?    (別のUSB2.0 HSハブ)
```
どれか1つの交換で 480 になれば、その要素が原因。全て 12 のままなら i.MX28 PHY/microUSB 配線を疑う。

## 4. 質問(High-Speed リンク不成立の切り分け)

1. **HS 対応ルート+HS 対応ハブなのに upstream リンクが Full-Speed で確立する典型原因**は何か。
   HS chirp ハンドシェイクの信号品質(microUSB-OTG 変換の挿入損失・ケーブル長/品質・D+/D- 反射)/
   i.MX28 USB PHY の HS 較正 / ハブ個体・相性 / VBUS 立ち上がりタイミング、の実務的な多寡と、
   **microUSB→OTG 変換を1段挟むこと自体が HS を落とす**主因になり得るか。

2. **Stage1/2 の観測から原因を絞る解釈**。ハブ upstream=12 のまま/HS メモリ=480、といった各パターンが
   それぞれ何を示唆するか。特に「i.MX28 PHY は HS 可能だがハブとの間だけ FS」という切り分けの妥当性。

3. **ケーブル/OTG 変換/ハブの選び方**。HS chirp が通りやすい条件(短く高品質・USB2.0 認証・
   single-TT/multi-TT、セルフパワー品質)。交換で 480 を得られる見込みと最短手順。

4. **PHY(DTB)調整は最後の手段**という理解で正しいか。仮にハード交換で解決しない場合に限り、
   `fsl,imx28-usbphy` で有効な HS 較正プロパティ(`fsl,tx-cal-45-dn/dp-ohms`, `fsl,tx-d-cal`,
   `tx-preemp-amp-tune` 等)の定石を知りたい。※`maximum-speed="high-speed"` は「能力上限の指定」で
   あって「HS を強制する魔法ではない」、`itc-setting` は速度ネゴとは無関係、という理解で合っているか。

5. **HS 成立の検証観点**。`1-1/speed=480` 以外に、`usb 1-1: new high-speed USB device`、HS chirp の
   retry が無いか、512B バルク descriptor が読めるか等、dmesg/デバッグで確認すべき点。

6. **i.MX28(mxs-phy)+ 外部ハブの HS 既知問題**があれば(ci_hdrc/mxs-phy と特定ハブの相性、
   VBUS/OTG 経路が HS ネゴを阻害する既知パターン、対策コミット等)。

7. (優先度低)**FS で割り切る場合**の可否。もし PW-SH6 の物理経路が HS を確立できないと判明したら、
   Full-Speed(64B)でも実用になる USB WiFi の選択肢はあるか。ただしこれは**問題の差し替え**に
   なりかねないので、まず Stage1-3 で「HS リンクを成立させられるか」を確定させたい。

## 5. 到達点(表現を厳密化)

- カーネル再ビルド成功(6.1.70、`CONFIG_BT` 開通=BLE 用 Bluetooth スタック稼働)。
- ath9k endpoint 検査は**復元が正解**(FS descriptor を正しく弾いてハング防止)。安全カーネル
  (検査復元 + BT)を常用ベースに配備済み。
- **UWF-1 は HS 接続の x86 環境では正常動作を確認済み。PW-SH6 でも HS 接続が成立すれば ath9k_htc を
  無改造で使える可能性は高いが、Brain 上での「HS 接続 + UWF-1 動作」はまだ未検証**(過度な断定を避ける)。
