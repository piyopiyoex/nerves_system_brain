## 1. 目的と最初のゴール

SHARP の電子辞書「Brain」シリーズを Nerves(Elixir) で動かし、
既存の KIOSK フレームワーク資産（hello_kiosk_7inch / hello_kiosk_raspad3 の
Elixir 駆動描画）を移植可能な、キーボード付き小型 KIOSK 端末に仕立てる。

Brain は「物理キーボード + タッチ + 小型 LCD + microSD ブート可能」という
希少なフォームファクタで、SD カードを抜けば元の電子辞書に戻る（本体 NAND
非破壊）ため、実験プラットフォームとして安全性が高い。

**本プロジェクトの最初のゴール**（ここまで通れば「Nerves 化する技術的根拠が得られた」と判断する）:

> 実機 **PW-SH6** で、**Brainux + USB-NCM + BEAM/Elixir + /dev/fb0 描画** の4点を成立させる

完全な Nerves システムの完成は最初のゴールにしない（§5 Phase 3 参照）。

## 2. 対象ハードウェアの整理

### 2.1 対象機種: PW-SH6（確定）

対象実機は **PW-SH6**（Sx6 世代・2019年1月24日発売・高校生モデル）に確定した。
世代の位置づけ: Brainux の Linux ブート対応は PW-Sx1〜Sx7 世代（i.MX283）が中心で、
PW-SH6 はその中に含まれる。最新の x1/x2 世代（i.MX7 系）は LCD 等未対応で対象外。

PW-SH6 のプロファイル:

### 2.2 i.MX283（PW-SH6 の SoC）の仕様と Nerves 観点での意味

| 項目 | 内容 | Nerves への影響 |
|---|---|---|
| CPU | ARM926EJ-S 454MHz (**ARMv5TEJ**) | 公式 Nerves system/toolchain が存在しない。FPU 無し → **soft-float** ビルド必須。ただし真の難所は toolchain ではなく **OTP/BEAM の成立性**（§3） |
| RAM | **128 MiB** | 「BEAM が起動する」ことと「Nerves アプリが実用になる」ことは別。Phase 1-B で実測して判断 |
| ブート | on-chip BootROM が SD 上の `u-boot.sb`(SB形式) をロード | U-Boot ベースのブートチェーン → Nerves の標準構成と親和性が高い |
| LCD | mxsfb フレームバッファ (`/dev/fb0`)、**854×480**（DMA 未使用） | Elixir から fb 直描画方式が移植可能（§5 Phase 4） |
| ネットワーク | WiFi/Ethernet 非搭載。**USB Ethernet Gadget (NCM) が Brainux で動作済み** | 2026-03 リリースで RNDIS→NCM に移行済み、Linux/macOS/Windows で認識確認済み。これを Nerves 側でもそのまま利用する（本提案の強み）。WiFi .env 焼き込み問題とは構造的に無縁 |
| キーボード | Sx6 世代で対応済み | evdev 経由で入力取得可 |
| タッチ | 動くが座標がずれる状態（Wiki 記載） | 座標補正で対応（向き・レイアウトは変えない方針） |
| 音声 | Brainux 標準構成では未対応（録音・再生とも） | **本プロジェクトの必須要件として扱わない**。優先順位は LCD/Keyboard/USB → Touch → Audio とし、Audio は将来課題として残す |
| 電源制御 | 電源コントローラ未対応の機種あり | シャットダウンは `poweroff` 運用、機種による |

### 2.3 ブートの仕組みと buildbrain の構成

```
[電源ON]
  i.MX283 BootROM
    ├─ (A) WinCE 経由: NAND → Windows CE 起動
    │        └─ WinCE 上のアプリ「BrainLILO」→ SD の U-Boot へジャンプ
    └─ (B) 直接SDブート: BootROM が SD の u-boot.sb を直接ロード
             （PW-SH6 は不可リストに含まれず可能見込み。nk の内容を boot 直下へ配置）
  → U-Boot (brain-hackers フォーク、機種フィンガープリントで判別)
  → Linux カーネル (brain-hackers/linux-brain)
  → rootfs
```

**PW-SH6 での起動経路の方針**: PW-SH6 はファームウェア Ver.3.7 以降で非公式アプリ起動の
保護（Sx7 世代の対策のバックポート）が入っており、経路(A) の WinCE 経由起動は
本体ファームウェア版数によって手順が変わる（Brain Wiki の世代別「アプリの起動方法」参照）。
このため本プロジェクトでは **経路(B) 直接 SD ブートを第一候補**とする。
直接ブートなら WinCE 側の保護と無関係に、電源投入（リセット）だけで Nerves が立ち上がる
運用になり、KIOSK 用途とも相性が良い。Phase 0 で両経路を実機確認し確定する。

[buildbrain](https://github.com/brain-hackers/buildbrain) は単なるイメージ生成環境ではなく、
**Linux kernel / U-Boot / boot4u / brainlilo / Debian rootfs / Buildroot / SD イメージ生成**
までを含む統合ビルド環境として現在もメンテナンスされている。
2026-03-25 リリース時点で **Linux 6.1 / Debian 13.4 "Trixie" / USB NCM** に更新されており、
「古い機械だから Linux 環境も古い」という状況ではない。今の Brainux を土台に PoC する
判断は妥当性が高い。

Nerves 化の基本戦略はこのチェーンの **rootfs 以降だけ**を Nerves 製 (erlinit + BEAM) に
差し替えること。U-Boot・カーネル・Device Tree は brain-hackers の成果物を**固定して流用**する。

## 3. 最大の技術課題: ARMv5 soft-float 上で実用的な OTP/BEAM/Elixir を確定すること

「ARMv5 だから soft-float toolchain が要る」は正しいが、それは難所の入口にすぎない。
本当の課題は、以下の**全経路を成立させる**ことである:

```
Elixir → BEAM → Erlang/OTP → libc → ARMv5 soft-float → i.MX283
```

現在の Nerves は新しめの OTP/Buildroot を前提に進んでおり、公式最小ターゲットの
rpi0 でさえ ARM1176(ARMv6)/512MB である。「nerves_toolchain_ctng を少し変更すればいける」
と楽観せず、**古い ARM アーキテクチャでどの OTP まで実用になるかを最初に確定する**。

方針: **最新 Elixir/OTP を使うことを目的にしない**。実機で成立する最も新しい組み合わせを探す。

| 候補 | OTP | Elixir | 備考 |
|---|---|---|---|
| A | OTP 27 | 1.18 | **✅ 実機で成立確認（2026-09-02）: Debian trixie armel の erlang-base 27.3.4.1 が動作、BEAM RSS 約20〜23MB** |
| B | OTP 26 | 1.17 | 不要（A が成立） |
| C | OTP 25 | 1.15 | 不要 |
| D | OTP 24 | 1.14 | 不要 |

**→ 2026-09-02 実機検証により候補 A（OTP 27）で確定。本計画の最大リスクは解消した。**

確定作業は Phase 1（Brainux 上、Debian armel パッケージ + 必要ならクロスビルド/qemu-user chroot）
で行い、その結果を Phase 2 以降のバージョン固定に用いる。

## 4. 構築方法の比較（3案）

### 案A: Brainux カーネル固定 + Nerves rootfs 差し替え【本命】

v1.0 の「フルカスタム Nerves system」から変更。**最初から全部を Nerves 流に作り直さない**。

```
Brainux 資産（固定・流用）          Nerves 側（本プロジェクトで作る）
 ├─ U-Boot (u-boot-brain)           └─ rootfs
 ├─ Linux kernel (linux-brain)           ├─ erlinit
 └─ Device Tree                          ├─ BEAM / OTP（Phase 1 で確定した版）
                                         ├─ Elixir
                                         └─ hello_kiosk_brain アプリ
```

- 第1段階のゴール: `Brain BootROM → Brain U-Boot → Brain kernel → Nerves rootfs → erlinit → BEAM → hello_kiosk_brain`
  が起動すること。これで「Brain の Linux ハードウェア層」と「Nerves のアプリ層」の接続が実証される
- 第2段階（成功後に追加）: fwup / A/B パーティション / USB-NCM 経由ファームウェア更新 / read-only rootfs
- ツールチェーン: armv5tej soft-float を `nerves_toolchain_ctng` で自作（OTP バージョンは Phase 1 の結果で固定）
- 長所: 問題の切り分けが容易（U-Boot/kernel は動作実績あるものに触らない）。段階的に Nerves の利点を追加できる
- 短所: 工数は3案中最大。ARMv5 + OTP + Buildroot + fwup の組み合わせは前例が乏しい

### 案B: Brainux (Debian armel) の上に Erlang/Elixir を載せる【PoC・検証用】

Brainux は Debian ベース（armel = ARMv5 soft-float）なので
`apt install erlang` 相当で BEAM が動く可能性が高い。

- 長所: 最短で §3 の成立性（BEAM が動くか / RAM 128MB で実用になるか / 使える OTP 版）を実証できる。
  カーネル・ドライバ・USB-NCM は Brainux 側で解決済みのものに乗れる
- 短所: Nerves ではない（ファーム更新機構無し、起動遅い、書き込み可 rootfs の破損リスク）。
  Debian armel の Erlang バージョンが古い可能性

### 案C: AtomVM (generic_unix) を Brainux 上で動かす【軽量代替・保険】

AtomDeck / hello_atomvm で実績のある AtomVM を ARMv5 向けにクロスビルドして Brainux 上で動かす。

- 長所: メモリフットプリント最小。既存 AtomVM 資産（シナリオ JSON 等）を流用可能
- 短所: Nerves ではない。フル OTP が使えず、fb 描画や USB ガジェット管理を自前実装

### 推奨: 案B → 案A の二段構え

1. 案B で Phase 0〜1 を実施し、最初のゴール（Brainux + USB-NCM + BEAM/Elixir + /dev/fb0）を達成する
2. 成立を確認してから案A に着手する
3. 案C は Phase 1-B で BEAM のメモリ/性能が実用に達しないと判明した場合の保険とする

## 5. 詳細手順（推奨ルート）

### Phase 0: PW-SH6 での Brainux 動作確認

1. 本体の**ファームウェア版数を確認**する（Ver.3.7 以降なら非公式アプリ起動保護あり、§2.3）
2. [buildbrain releases](https://github.com/brain-hackers/buildbrain/releases) から
   **PW-SH6 対応（Sx6 世代）のイメージ ZIP** を取得し、balenaEtcher または `dd` で
   microSD (4GB以上、高耐久品) に書き込み
3. **起動経路の確定（§2.3）**:
   - まず**直接 SD ブート**を試す: `nk` ディレクトリの内容をブートパーティション直下へ
     コピーし、SD を挿してリセット → U-Boot が直接立ち上がるか確認
   - 不可だった場合のみ WinCE 経由（BrainLILO）にフォールバックし、ファーム版数に応じた
     起動手順を Brain Wiki「アプリの起動方法」で確認する
   - ログイン: user / brain
   - 終了は必ず `sudo shutdown -h now`（強制断は SD 破損リスク）
4. 確認項目: LCD 表示（854×480）/ キーボード / タッチ座標ずれの程度 /
   **USB-NCM で母艦(Linux)と疎通** / `free -m` で空き RAM /
   `brainux_version` ファイルでイメージ版を記録 → §2.1 の「残り要確認」欄を確定させる

### Phase 1: Brainux 上で BEAM 検証（案B）

#### Phase 1-A: 起動確認

1. `apt` で erlang を導入（armel）。動かなければ kerl/ソースビルド
   （実機ビルドは遅いので、母艦での armel クロスビルド or qemu-user chroot を優先）
2. `erl` 起動 → Elixir を配置して IEx 起動
3. §3 の候補表に沿って、**成立する最も新しい OTP/Elixir の組み合わせを確定**する

#### Phase 1-B: 実用性測定（起動確認だけで終わらせない）

「BEAM が起動する」と「Nerves アプリが実用になる」は別。以下を段階的に確認・計測する:

```
erl 起動 → BEAM 常駐 RAM → Elixir 起動 → OTP アプリ起動
 → GenServer → Supervisor → File → Port → USB-NCM 通信 → fb0 描画
```

- 計測コマンド: `free -m` / `cat /proc/meminfo` / `ps`（OS 側）、`:erlang.memory()`（BEAM 側）
- OTP アプリの実起動: `{:ok, _} = Application.ensure_all_started(:logger)` 等
- Port 経由で外部プロセス起動（Nerves で多用するため必須確認）
- `/dev/fb0` への直書きテスト（まず `cat /dev/urandom > /dev/fb0` レベル、次に Elixir の Port/NIF から）
- USB-NCM 上で SSH/scp が実用速度か

**Phase 1 完了条件 = 最初のゴール達成**: Brainux + USB-NCM + BEAM/Elixir + /dev/fb0 の4点成立。
ここで RAM/性能が不足なら案C へ切替判断。

### Phase 2: カスタムツールチェーン作成

- `nerves_toolchain_ctng` を fork し、crosstool-NG 設定を
  **arm926ej-s / ARMv5TEJ / soft-float / glibc(or musl)** で作成
- 命名例: `nerves_toolchain_armv5tej_nerves_linux_gnueabi`
- OTP/Elixir は **Phase 1 で確定した版に固定**してビルド
- 検証: ビルドした gcc + OTP で hello world / erl を作り、実機(Brainux上)で実行

### Phase 3: Nerves rootfs 差し替え（`nerves_system_brain`）

**第1段階のゴールは「Nerves rootfs だけの差し替え」**。U-Boot / kernel / Device Tree は
brain-hackers 成果物（buildbrain の該当リリース）を**コミット/リリース番号で pin して固定流用**し、
最初は一切変更しない。全部を同時に触ると問題の切り分けができなくなる。

1. **rootfs 構築**: `nerves_system_br` ベースの Buildroot で armv5(soft-float) rootfs を生成
   （`BR2_arm926t`）。カーネルはビルドしない（Brainux の kernel/modules を流用）
2. **SD 構成（第1段階）**: buildbrain のパーティションレイアウトを踏襲し、
   rootfs パーティションだけ Nerves 製に差し替え。起動は Phase 0 で確定した経路
   （第一候補: 直接 SD ブート）を用いる
3. **erlinit.config**: コンソールは USB ガジェット ACM またはログファイルで確保
   （実機 UART が取れない前提で設計）
4. **起動確認**: `BootROM → U-Boot → linux-brain → Nerves rootfs → erlinit → BEAM → IEx(SSH)`
5. **第2段階（起動成立後に追加）**: fwup.conf 設計（ブート領域 / rootfs A/B / アプリデータ、
   BrainLILO 用 FAT 領域の同居）、read-only rootfs 化、`ssh_subsystem_fwup` 導入
6. **アプリ側 mix.exs**: `NERVES_SYSTEM_*_PATH` はヘルパー関数で解決する
   （hello_rpi3a_lcd_spi_eth で確立した方式を踏襲）

### Phase 4: hello アプリと KIOSK 移植

1. ネットワーク: **Brainux で動作実績のある USB-NCM 構成を Nerves 側でも再現**し、
   `nerves_ssh` で母艦から SSH 接続（リンクローカル or 固定 IP、例: 172.31.x.x/30）
   - Brainux では `sudo brain-config` がガジェット有効化を担っている（実機で確認済み）。
     Nerves 化の際は brain-config が設定している内容（configfs のガジェット構成・
     カーネルモジュール・IP 設定）を調べて Nerves rootfs の起動時処理として再現する
2. **fb 描画: LovyanGFX は移植しない**。ARMv5 への C++ ライブラリ移植を避け、
   KIOSK 用途に必要な薄い描画 API（`fill_rect` / `draw_bitmap` / `draw_text` 程度）を
   fb0 直書きの Port/NIF として自作し、既存 KIOSK 資産とはバックエンド抽象化で接続する:

   ```
   hello_kiosk_7inch / raspad3 / brain（アプリ層）
           │  共通描画 API
           ▼
   ┌────────────────┐
   │ Kiosk Renderer │
   └───────┬────────┘
           ├─ RPi backend（既存: LovyanGFX）
           └─ Brain backend（新規: /dev/fb0 直書き）
   ```

   - RGB565 の色バイト順は実機で必ず確認（kiosk_7inch での既知の教訓）
   - 右上 IP 表示（raspad3 方式）は USB-NCM の IP を表示
3. キーボード: `input_event` で evdev 取得 → KIOSK 操作系にマップ
4. タッチ: 座標補正のみで対応（**画面の向き・レイアウト前提は変更しない**）
5. **ファームウェア更新**: 「OTA」ではなく **USB-NCM 経由ファームウェア更新**と呼ぶ
   （母艦 → USB → SSH → fwup → SD）。運用が安定したら、母艦を Raspberry Pi に置き換えて
   `RPi → USB → Brain` の常設更新・管理構成にできる（KIOSK 用途では有望な構成）

## 6. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **ARMv5 soft-float で実用的な OTP/BEAM/Elixir の組み合わせが確定できない（最大リスク）** | 計画全体 | Phase 1 で §3 の候補表を上から順に実機検証し、成立する最新版を確定してから先へ進む。OTP 24 まで落として不成立なら案C へ |
| RAM 128MB で「起動はするが実用にならない」 | アプリ規模制限 | Phase 1-B で GenServer/Supervisor/Port/描画まで含めて実測。厳しければ案C (AtomVM) へ切替 |
| DMA 未使用 fb で描画性能不足 | 描画がもたつく | 薄い自作描画 API で部分更新中心に設計。静的サイネージ用途に限定 |
| 音声が必須要件化する | 機能不足 | 本機は「表示+キー入力 KIOSK」を主用途とし、Audio は優先度最下位の将来課題として扱う |
| PW-SH6 で直接 SD ブートが実機で不成立 | 電源投入だけで Nerves が起動しない | WinCE 経由（BrainLILO）にフォールバック。ただしファーム Ver.3.7 以降の起動保護があるため、Brain Wiki の世代別起動手順で回避方法を確認する。本体ファームの安易な更新は行わない |
| SD カード故障・電源断・boot 領域破損・fwup 設計ミス | 起動不能 | read-only rootfs + A/B 構成は「rootfs の書き込み頻度を抑え、FS 破損リスクを大幅に低減する」施策であり万能ではない。高耐久 SD + 予備 SD の複製運用を併用 |
| コミュニティ資産の更新停滞 | カーネル等のメンテ | 使用コミット/リリースを pin して自リポジトリに fork（buildbrain は 2026-03 時点で活発に更新中） |

## 7. 工数見積り（目安）

「5日でできたらラッキー」水準の組み合わせ（ARMv5 + OTP + Buildroot + Nerves + fwup）である
前提で、初版より保守的に見積もる。

| フェーズ | 内容 | 目安 |
|---|---|---|
| Phase 0 | PW-SH6 での Brainux 起動確認 + 起動経路確定 | 0.5〜1日 |
| Phase 1 | BEAM/Elixir PoC + 実用性測定 + OTP 版確定 | 2〜4日 |
| Phase 2 | armv5 ツールチェーン + OTP ビルド | 2〜5日 |
| Phase 3 | Nerves rootfs 差し替え → fwup/A/B 化 | 1〜3週間 |
| Phase 4 | KIOSK アプリ移植（描画バックエンド新規作成含む） | 3〜7日 |

## 8. まとめ

- 対象実機は **PW-SH6**（Sx6 世代 / i.MX283 / 854×480）。brain-hackers コミュニティの資産
  （U-Boot / linux-brain / buildbrain）により Linux ブートが確立しており、2026-03 時点でも Linux 6.1 / Debian 13.4 /
  USB NCM と活発に更新されている。**今の Brainux を土台に PoC する価値は高い**
- **最大の技術課題は、ARMv5 soft-float 上で実用的な OTP/BEAM/Elixir の組み合わせを
  確定すること**。toolchain 自作はその手段にすぎない。最新版を使うことを目的にせず、
  実機で成立する最も新しい組み合わせを Phase 1 で確定する
- 案A は「フルカスタム system」ではなく **「Brainux の U-Boot/kernel を固定し、
  Nerves rootfs だけを差し替える」**構成とし、成立後に fwup/A/B/read-only を段階追加する
- 描画は LovyanGFX を移植せず、**/dev/fb0 直書きの薄い描画 API + Kiosk Renderer の
  バックエンド抽象化**で既存 KIOSK 資産と接続する
- ネットワークは Brainux で動作実績のある **USB-NCM** を採用（Linux/macOS/Windows 認識確認済み）。
  ファームウェア更新は「USB-NCM 経由ファームウェア更新」として設計し、将来は RPi 母艦による
  常設管理構成へ発展させられる
- PW-SH6 はファーム Ver.3.7 以降に非公式アプリ起動保護があるため、起動経路は
  **直接 SD ブートを第一候補**とする（WinCE 経由はフォールバック）
- 推奨ルートは **案B(Brainux PoC) → 案A(Nerves rootfs 差し替え)** の二段構え。
  最初のゴールは「PW-SH6 実機で Brainux + USB-NCM + BEAM/Elixir + /dev/fb0 を成立させる」こと
